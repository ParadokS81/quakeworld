# Arc 1 — locked cross-cutting decisions

These choices apply to every phase. Each phase MD must respect them. If any phase needs to deviate, surface a "deviation" section at the top of that phase MD and stop for operator review — do not silently override.

The decisions here resolve issues found during review of the legacy monolithic plan (see `review-findings.md`). They are NOT open questions; they are commitments.

---

## D1. Foreign-key convention — keep `entity_id INTEGER`

**Decision:** Layer 1 ports `entities.id INTEGER PRIMARY KEY` + `canonical_id TEXT UNIQUE`. Every `*_versions` table FKs on `entity_id` (the integer PK), exactly as today. `change_events`, `source_state_transitions`, `source_overrides` keep their `entity_id` columns.

**Why:** The architecture spec says "the existing Layer 1 schema is preserved structurally, ported to Postgres dialect" (`docs/superpowers/specs/2026-05-01-qw-oracle-database-architecture-design.md:349`). The legacy plan flattened to `canonical_id`-as-PK, which would force a rewrite of every loader adapter, MCP tool query, and snapshot builder. Faithful port is smaller, safer, and matches operator intent.

**Implication:** Asset relation tables (`asset_extensions`, `asset_path_rules`, `asset_cvar_bindings`, `asset_loader_sites`) keep their existing FK style — they reference `entities(canonical_id)` because that's the existing shape. Two FK conventions coexist exactly as in SQLite. Don't "tidy this up."

## D2. Runtime — Bun for everything

**Decision:** All scripts (loader, embed, eval, calibrate, migrator) and all tests run under Bun. Drop `tsx` from devDependencies. `package.json` scripts use `bun` instead of `tsx`.

**Why:** The legacy plan mixed `tsx` (Node) and `bun test`. Every CLI entry point used `if (import.meta.main)` — a Bun-only feature. Under tsx (Node 20), that guard is always falsy, so every script silently no-ops on `npm run <script>`. Verified: `node v20.20.0` does not define `import.meta.main`. The MCP server already runs on Bun. Going single-runtime eliminates an entire class of bugs and matches what's already working.

**Implication:** `import.meta.main` guards are valid and stay. CLI scripts run via `bun scripts/.../index.ts` instead of `tsx scripts/.../index.ts`. Tests use `bun test`. `package.json` scripts:

```json
"migrate": "bun db/migrate.ts",
"load-knowledge": "bun scripts/load-knowledge/index.ts",
"load-concepts": "bun scripts/load-concepts/index.ts",
...
```

If a script truly needs Node-only behavior, surface it as a deviation; otherwise Bun.

## D3. Schema-as-generator — do not hand-type CREATE TABLE

**Decision:** Phase 2 writes a one-shot generator script (`scripts/generate-pg-migration.ts` or similar) that reads `apps/qw-oracle/scripts/load-knowledge/schema.ts` and emits Postgres-dialect migration SQL. The phase MD describes the generator and the review process; it does NOT inline 14+ CREATE TABLE blocks.

**Why:** Most of the grave issues in the legacy plan review (wrong CHECK enum values, wrong column lists, missing tables, missing UNIQUE constraints on `change_events`) came from the plan author hand-typing migrations from memory. Generating from the live `schema.ts` (which is the working source of truth for SQLite) eliminates this category in one move.

**Implication:** Phase 2's deliverable is the generator + the generated migration files + a verification step that diffs `\d+ <table>` between SQLite (current `data/knowledge.db`) and Postgres (after migrate). Nothing is hand-typed for the per-version tables. The generator handles SQLite→Postgres dialect quirks: `INTEGER PRIMARY KEY` → `BIGSERIAL PRIMARY KEY` or `INTEGER GENERATED BY DEFAULT AS IDENTITY`, `TEXT` types unchanged, `INTEGER NOT NULL DEFAULT 0` for booleans → `BOOLEAN NOT NULL DEFAULT FALSE`, ISO-string timestamps → `TIMESTAMPTZ`, JSON stored as `TEXT` → `JSONB`.

The generator is throwaway after the migration ships. Schema evolution post-Arc-1 happens via append-only `.sql` migrations, not via re-running the generator.

## D4. Schema completeness — port ALL 31 tables

**Decision:** Phase 2 ports the full 31-table v18 inventory listed in `apps/qw-oracle/SCHEMA.md:18-29`. No table is "deferred to a later arc" unless explicitly listed in D5 below. The generator (D3) makes this trivial — run it, every CREATE TABLE in `schema.ts` becomes a Postgres CREATE TABLE.

**The 31 tables, by group:**

- Identity: `versions`, `entities`
- Per-type version arc (15): `cvar_versions`, `command_versions`, `macro_versions`, `cmdline_param_versions`, `keyname_versions`, `hud_element_versions`, `ruleset_versions`, `token_primitive_versions`, `asset_category_versions`, `flag_bit_versions`, `cvar_alias_versions`, `protocol_message_versions`, `info_key_versions`, `log_template_versions`, `qc_builtin_versions`
- Relations (5): `asset_extensions`, `asset_path_rules`, `asset_cvar_bindings`, `asset_loader_sites`, `release_notes`
- qw namespace (4): `maps`, `gameplay_sources`, `gameplay_entity_defs`, `gameplay_mechanics`
- Change tracking (3): `change_events`, `relation_changes`, `source_overrides`
- Audit (2): `source_state_transitions`, `schema_meta`

**Rename caution:** the qw-namespace tables are `maps` / `gameplay_sources` / `gameplay_entity_defs` / `gameplay_mechanics` — NOT `qw_maps` / `qw_entity_defs` / `qw_mechanics` as the legacy plan claimed. Keep existing names. `gameplay_sources` is the project/version anchor that the entity-defs and mechanics tables FK to; do not omit it.

**`schema_meta` collision:** the SQLite `schema_meta` is a `(key, value)` table holding the schema version. The Postgres migrator also wants a `schema_meta`-style table tracking applied migrations. Resolve by:
- Migrator's table is named `schema_migrations` (filename, applied_at, sha256).
- The SQLite-equivalent (key, value) metadata table is named `oracle_meta` and holds `schema_version`, `last_full_rebuild`, etc. (Legacy plan got this part right.)

## D6. `entities.description` — derive from latest per-version row

**Decision:** Phase 2 adds a step that populates `entities.description` from the per-version table at `last_seen_version`. For most types this is `<type>_versions.help_desc` at `version = entities.last_seen_version`. The derivation runs as part of the loader's post-load pass (after all per-version rows are upserted) and is recomputed whenever `last_seen_version` changes.

**Why:** The legacy plan added `description_tsv` and `description_embedding` columns on `entities` without populating `description`. The current loader writes help text per-version, never on the entities row. Without derivation, the lexical and vector indexes are empty and `search_entities` returns nothing. Issue #7 in the review.

**Implementation:** Phase 2 specifies the derivation as either a SQL view, a trigger, or an explicit step in `load-version.ts`. Phase plan picks one with reasoning; whichever it picks, phase verification asserts that for every entity with help text in the per-version table, `entities.description` is non-empty.

**Per-type mapping** (the generator can emit this from schema.ts column inspection):
- `cvar` → `cvar_versions.help_desc` (longest non-null wins if multiple help_* columns have content; concat with newlines is also acceptable)
- `command` → `command_versions.help_desc`
- `macro` → `macro_versions.help_desc`
- `cmdline_param` → `cmdline_param_versions.help_desc`
- `hud_element` → `hud_element_versions.help_desc`
- `ruleset` → null/empty (no help text; rely on name + locked-cvars JSON for retrieval)
- `keyname` → null (no help text)
- `token_primitive` → derive from category + form (e.g., "LED color blue" for `$B`)
- `flag_bit` → bitmask_family + name
- `cvar_alias` → "alias of <target_canonical_id>" + drift status sentence
- `protocol_message` → `protocol_message_versions.description` (verify column name)
- `info_key` → `info_key_versions.description` (verify)
- `log_template` → `log_template_versions.description` (verify)
- `qc_builtin` → `qc_builtin_versions.description` (verify)
- `asset_category` → `asset_category_versions.description`

Phase 2 verifies the actual column names against `schema.ts` before locking the mapping.

## D7. Layer 2 chat search — language-agnostic tsvector

**Decision:** `messages.content_tsv` and `session_search.session_tsv` use `to_tsvector('simple', ...)`, NOT `to_tsvector('english', ...)`.

**Why:** Discord and IRC corpus is mixed-language (English / Swedish / Russian / others; the IRC encoding gap memo notes substantial non-English content). English stemming and stop-words mangle non-English tokens. SQLite FTS5 was language-agnostic; switching to English stemming is a quality regression. `simple` config does no stemming and no stop-word removal — closest to FTS5 default behavior.

**Implication:** Tradeoff is that English queries match exact tokens only ("running" doesn't match "runs"). Acceptable for a chat corpus where users tend to repeat verbatim terminology. Layer 1 entity descriptions and Layer 3 concept chunks stay on `'english'` because those corpora are curated English content.

## D8. Embedding-space verification — assert at startup

**Decision:** MCP server startup asserts that `voyage-4-large` and `voyage-4-lite` produce comparable vectors. Concrete check:
1. Embed a known string (e.g., `"weapon scripts"`) with the build model (`voyage-4-large`).
2. Embed the same string with the query model (`voyage-4-lite`).
3. Assert cosine similarity ≥ 0.85. If lower, refuse to start with a clear error: "build/query embedding spaces appear divergent; verify Voyage 4-series shared-space claim."

Cache this check's result in `oracle_meta` so it runs once per startup, not per request.

**Why:** The architecture spec asserts "shared embedding space" without testing it. Dimension match (1024) is necessary but not sufficient. If geometries diverge silently, vector search returns garbage with no error signal.

**Implication:** First Voyage call on startup is a verification call (counts against `embedding_api_log`). Acceptable — runs once per server boot.

## D9 (revised 2026-05-02). Layer 2 is Discord-only in Arc 1

**Decision:** Layer 2 corpus in Arc 1 covers **Discord only**. IRC is excluded entirely. The `messages.platform` column drops the `'irc'` enum value (or the column is removed entirely if a single-platform contract is cleaner). No IRC importer, no IRC parser, no mojibake baseline machinery, no `mirc-logs/` traversal.

**Why:** IRC content is mostly low-signal noise (channel join/part, status messages, repetitive bot output) and pre-2016 non-English content is corrupted at the codepage level. Discord covers 9+ years of substantive community chatter and is the actual signal source for `search_solved_issues`. Carrying IRC forward through Arc 1 spends complexity budget on a corpus the operator doesn't intend to query.

**Original D9 (deprecated):** The earlier version of D9 said "ship with the known IRC corruption, document it, defer the codepage re-import to Arc 3." That was a lesser fix; full exclusion is better. The deprecated text is preserved in git history (`d4f98c2`) for reference.

**Implication for the redrafted Phase 3:**
- `messages.platform` enum: `CHECK (platform = 'discord')`, or drop the column entirely.
- Drop the `import-irc.ts` task and all IRC-shaped tests.
- Drop the mojibake baseline verification gate.
- Drop the `mirc-logs/` directory references in CLAUDE.md status prose; the Layer 2 status section now says "Discord-only; IRC deferred to Arc 3 alongside any future re-import work."
- `search_solved_issues` (Phase 6) operates on a single-platform corpus — slight simplification.
- Eval queries (Phase 8) cite Discord sessions only.

**Reconsider in Arc 3** if and only if (a) the codepage re-import work makes IRC content trustworthy, AND (b) operator demand exists for IRC-era queries. Otherwise IRC stays out indefinitely.

**F9 / F13 status under D9-revised:** F9 (English stemming on mixed-language chat) still resolves via `'simple'` config since Discord itself has multi-language content (Swedish / Russian / German names, etc.) — the decision text in D7 stands. F13 (IRC encoding gap) is **dissolved** — the gap doesn't apply to a corpus that doesn't contain IRC.

## D10. Eval set vs calibration set — holdout split

**Decision:** Operator authors **two** disjoint query sets:
- `eval/eval-queries.json` (10-15 queries) — used by `eval.ts` to compute recall@1/recall@3 for the deploy gate.
- `eval/calibration-queries.json` (5-8 queries) — used by `calibrate.ts` to sweep match-quality thresholds.

`calibrate.ts` does NOT read `eval-queries.json`. `eval.ts` does NOT read `calibration-queries.json`.

**Why:** Legacy plan let calibration sweep thresholds against the same set the deploy gate evaluated, making the gate trivially passable post-calibration (overfit to test set). Disjoint splits are the standard fix.

**Implication:** Phase 8 prerequisites task asks the operator to author both sets before kicking off Phase 8. Calibration set can be smaller because thresholds are coarser-grained.

## D11. Eval out-of-corpus scoring — score by `match_quality`, not by hit count

**Decision:** For eval queries with `expected_top_3: []` (out-of-corpus / refusal expectations), eval scores success as `result.match_quality === 'none' || result.match_quality === 'weak'`. Hit count does NOT matter — hybrid retrieval almost always returns *something*; what matters is whether the tool correctly labels low confidence.

**Why:** Legacy plan's `top1Hit = q.expected_top_3.length === 0 ? allHits.length === 0 : ...` penalized the tool for retrieving anything on out-of-corpus queries. The honest-failure machinery's whole point is that the tool retrieves chunks but labels them weakly. The eval should reward that, not punish it.

**Implication:** `eval.ts` checks `match_quality` for the empty-expected case and `rank` membership for the populated case. Two distinct codepaths.

## D12. Comments and prose — operator's output discipline

ASCII-only. No emoji. No em-dashes / en-dashes — use ASCII hyphen-minus. No marketing voice. Code comments explain WHY, not WHAT (per `apps/qw-oracle/CLAUDE.md` and the philosophy docs auto-loaded into the project).

This is enforced because the operator runs `docs-check` style validation and these patterns trigger noise.

## D13. Tests — Bun test runner, integration over unit, no mocks

**Decision:** Tests use `bun test`. Tests are integration-style: they hit a real Postgres test database (`qw_oracle_test`) at `127.0.0.1:5432` (separate database, same container as dev). No mocking of the DB layer.

**Why:** Aligns with `grug-brain.md` ("integration tests are the sweet spot"). The legacy plan mixed test styles — bun:sqlite in-memory for `maps.test.ts`, no clear pattern for new tests. Fix the test environment once, use it everywhere.

**Implication:** `package.json` script `test`: `DATABASE_URL=postgresql://qworacle:dev@localhost:5432/qw_oracle_test bun test`. Phase 1 creates the test DB alongside the dev DB. Test setup in each test file resets only the tables it touches (TRUNCATE-and-rebuild within a single file's `beforeAll`).

## D14. Phase atomicity — each phase commits a working state

Each phase ends with a commit that leaves the system runnable (per the legacy plan's phase table). If a phase mid-task leaves the system in a broken state, that's a phase-internal concern; phase boundaries must be green.

The phase MD's "Outputs to next phase" section names what's runnable at the end of the phase.

## D15. Verification at every phase boundary

Each phase MD ends with a "Verification" section listing copy-paste commands the operator runs to confirm the phase landed correctly. Verification commands return YES/NO answers, not interpretive prose. Examples:

```sql
-- Phase 2 verification: every CHECK constraint matches schema.ts
SELECT conname, pg_get_constraintdef(oid)
FROM pg_constraint
WHERE conrelid = 'entities'::regclass AND contype = 'c';
```

Operator runs the queries, eyeballs the output, decides whether to proceed to phase N+1. The fresh terminal does NOT auto-proceed.

## D16. No subagent execution for SQL migration writing

The fresh terminal drafts each phase as a markdown plan; sub-agents verify the draft against the codebase. Sub-agents do NOT write the migration SQL or the loader port code in this arc — that's execution, not planning. The plan files produced by the fresh terminal are inputs to a later, separate execution session (which will likely also be a fresh terminal).

This separation matches the operator's preference captured in memory (`feedback_no_subagents_for_mechanical_edits.md`): when the plan ships full file content / per-file diffs, execution is direct with Edit/Write/Bash, not via subagent.

## D18. Layer 2 port absorbs hygiene tightenings + reply-reference graph (2026-05-02)

**Decision:** Phase 3 absorbs four port-time hygiene tightenings from the Layer 2 hygiene design doc (`docs/superpowers/specs/2026-05-02-layer2-hygiene-design.md`) plus a reply-reference graph table. The post-Arc-1 "Layer 2 hygiene sidequest" is dissolved -- nothing of substance remains for it.

**What Phase 3 now does beyond the plain port:**

1. **Filter-then-segment.** `build-sessions.ts` drives session boundaries only over `category IN ('chat', 'link')`. Bot/reaction/system messages do NOT advance the gap clock and do NOT open sessions. Empty sessions disappear by construction. Gap threshold stays at 15 minutes (one algorithmic change at a time; if Phase 8 eval reveals the threshold is wrong, flip the constant then).

2. **`message_labels.session_id` is NULLABLE.** Label rows for bot/reaction/system messages are written with `session_id IS NULL`. Preserves the invariant that every imported message has exactly one label row. Session-scoped queries add `WHERE session_id IS NOT NULL`.

3. **`BOT_COMMAND_PATTERNS` dropped from `classify.ts`.** Discord exposes `author_is_bot` reliably; the regex slice was IRC-era and produces false positives on Discord content (.zip, .tar.gz, numeric expressions). The 359 human messages currently false-positive-flagged will be reclassified as 'chat' under the new shape -- which is correct.

4. **Duplicate `'xd'` removed from `REACTION_WORDS`.** `process-tier1.mjs:37` and `:39` both had `'xd'`; `Set` deduped silently but the duplicate is noise.

5. **`session_references` table.** Built post-segmentation from `messages.referenced_message_id`. Aggregates cross-session reply edge counts into `(source_session_id, target_session_id, reference_count)`. Within-session replies skipped. Phase 6's `search_solved_issues` will use this table. Phase 3 only builds it; Phase 6 queries it.

**Verification baselines (probed 2026-05-02 against `data/qw.db` before deletion):**

- Old session count (SQLite era, `process-tier1.mjs` algorithm): 88,214
- New session count (filter-then-segment): **84,369** (SQL window-function probe; see Task 5 in `phase-3-layer2-port.md`)
- `message_labels` row count: **717,389** (unchanged; every message still has one label row)

**Sidequest status:** The hygiene design doc's issues #2 (micro-session over-segmentation) and #6 (reply-chain-aware merging) remain open for a potential post-Arc-1 pass. No parking prompt for that work currently exists. The design doc at `docs/superpowers/specs/2026-05-02-layer2-hygiene-design.md` is the durable research artifact for anyone who picks it up.

**Encoding:** `docs/superpowers/plans/2026-05-02-qw-oracle-arc1/phase-3-layer2-port.md` Task 5 (filter-then-segment + classify hygiene) and Task 5b (build-session-references).
