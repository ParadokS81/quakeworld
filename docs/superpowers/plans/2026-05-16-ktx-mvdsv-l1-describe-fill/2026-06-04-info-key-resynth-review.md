### mvdsv `mtu:userinfo`  _[a]_

**New:** Client-published userinfo key holding the maximum transmission unit the client requests for the server-to-client connection, as an integer byte count (set from the ezQuake/FTE client-side mtu cvar). The server reads it once at connect time and uses it to size that client's network channel buffer: an empty or zero value keeps the legacy fixed buffer size, otherwise the server deducts the packet-header overhead and clamps the result to a sane range (no smaller than 1350 bytes, no larger than its own buffer ceiling). It is therefore a client suggestion the server honors within those bounds.

**What changed:** Draft said "Read by the server/mod" -- KTX has zero "mtu" references (grep clean), so the mod does not read it; only the mvdsv server does. Draft also omitted the load-bearing value semantics: it is an integer byte count applied to the per-client netchannel buffer, with an empty/zero value falling back to the legacy buffer size and non-zero values clamped to a minimum of 1350 bytes (after subtracting an 8-byte header) and capped at the server's buffer ceiling. The draft's core claim (client-set userinfo suggesting max packet size, honored if supported) was accurate.

### mvdsv `drate:userinfo`  _[a]_

The producing client cvar is defined by FTE (default 3000000); ezquake does not publish this key.

**What changed:** Draft substance was right (client-set, FTE cvar, bytes/sec download bandwidth) but two things were off: (1) it said "Read by the server/mod" -- ktx does NOT read drate (grep of ktx/src returned zero hits); it is read only by the server (mvdsv and FTE's own server). - **mvdsv `*client:userinfo`**: Holds the connecting client's engine name and build revision as a free-form string (for example "ezQuake 12345" -- alphabetic engine name followed by a numeric build/revision), published by the client itself into its own userinfo as a server-protected star-key. The mvdsv server reads this per-client value to identify ezQuake clients and parse their revision number, then uses it to gate engine-specific protocol extensions -- notably disabling the alpha-transparency (FTE_PEXT_TRANS) extension for client builds known to render it incorrectly.
- **mvdsv `*qtv:userinfo`**: Presence marker injected by a QTV proxy into the userinfo of the connection it makes to the game server on behalf of spectators. Only its presence matters -- the value string is not interpreted. When the server sees this key at connect time, it disables FTE protocol-extension negotiation for that connection, since those extensions do not work through a relaying proxy. As a protected star key, a normal client cannot set it; the proxy software is the only party that stamps it.
- **mvdsv `*skill:userinfo`**: Holds a bot's AI skill level as a decimal integer string (range 0-20). KTX stamps it on each bot's userinfo as a server-protected star key when the bot is spawned, so a human client cannot set or change it. The server reads it for bot clients and reports it in place of a real network ping (defaulting to 10 if the value is empty); it is also broadcast in the short userinfo other clients receive.
- **mvdsv `status:serverinfo`**: A serverinfo key holding the current match-phase as a free-form display string. The KTX mod writes it throughout a game's lifecycle: "Standby" at map load and whenever a match is idle or a countdown is aborted, "Countdown" while the pre-match countdown is running, "Forcestart" when an admin force-starts, and "N min left" giving the time remaining during an active match. The server reads it back to decide whether a game is in progress -- any value other than "Standby" is treated as started -- which gates QTV chat handling and blocks mid-game changes to physics settings such as pm_airstep unless the value is "Standby".
- **mvdsv `Qizmo:userinfo`**: Presence marker injected into a client's userinfo by the Qizmo proxy when a player connects through it. The value is never parsed -- only its presence matters -- so any client routed via Qizmo is recognized as proxied. The server reads it at connect time (alongside *qtv) and, when set, skips protocol-extension negotiation that cannot survive the proxy's passthrough; the mod also reads it to choose proxy-aware reconnect commands when forcing a player to spectator.
- **mvdsv `pmodel:userinfo`**: Holds the CRC checksum of the client's player model file (progs/player.mdl), computed and published by the client engine itself with a dedicated setinfo command at spawn -- it is not a user-settable cvar, and the client explicitly refuses any attempt to set pmodel or emodel by hand. The server reads it when a client spawns and broadcasts a warning if it is missing, or if it matches neither of the two checksums the server accepts for a standard player model; the check is advisory and does not block play.
- **mvdsv `dev:userinfo`**: A debug flag a client opts into by setting it to "1" via setinfo. When set, the server's server-side weapon-switching logic prints verbose diagnostics back to that client -- which weapon and impulse it selected as "best", hide-on-death decisions, firing-state transitions, and whether each switch attempt succeeded or failed. Any other value (or absence) keeps this trace output silent. Purely a per-client diagnostic toggle; it does not affect gameplay.
- **mvdsv `svf:userinfo`**: A client-set userinfo bitmask expressing a player's preference for how the server should treat their connection when all player slots are full. The server reads it only while the "force spectator on full" server setting is active. Bit value 1 opts the client IN to being automatically connected as a spectator when player slots are full but spectator slots remain; bit value 2 opts the client OUT of that automatic spectator fallback. Which bit applies depends on the server's force-spectator-on-full mode: the opt-in bit is honoured in the more aggressive mode, the opt-out bit in the milder default-on mode.
- **mvdsv `address:userinfo`**: A QTV relay's self-reported network address, supplied by the relay inside the USERINFO field of its QTV connection handshake (alongside its name and stream id). The server reads it when a relay opens a stream connection and stores it with that stream's destination record, where it identifies the relay in the server's QTV stream listing (shown as streamid@address). It is a free-form display/identification string, not a verified or enforced value.
- **mvdsv `qul:userinfo`**: Client-set opt-in flag (value "1") that subscribes the client to QTV user-list notifications. When set, the server pushes //qul messages to that client whenever a QTV spectator joins, leaves, or changes (and an initial full list on connect); the client's scoreboard renders those QTV viewers. Value "0" or absent means the client is not subscribed.
- **ktx `*client:userinfo`**: Client identity string the client publishes into its own userinfo, naming the client program and its build; ezQuake writes "ezQuake <revision>" where <revision> is the build number. KTX reads it to detect ezQuake and parse out that revision, which it then uses to gate version-dependent behavior (for example, enabling alias-parameter support and choosing the default hideplayers setting for older builds).
- **ktx `*state:userinfo`**: A server-computed, read-only per-client connection state, reported as one of: "free" (the client slot is empty and reusable), "zombie" (the client just disconnected and the slot is briefly held), "preconnected" (slot assigned but login/realip not yet settled), "connected" (in the server but not yet in the game) or "spawned" (fully in the game); any other value reports as "unknown". The client cannot set this key -- the server synthesizes it live from the client's connection lifecycle whenever it is queried. KTX reads it to count active players, to filter the unconnected/zombie entries shown by the klist command, and to locate a reconnecting player by userid or name.
- **ktx `login:userinfo`**: Holds the authenticated account name of a logged-in player, or an empty string if the player has not logged in. The value is set by the server when a client successfully authenticates -- either against the server's local account file (login command plus password) or against the central authentication website -- and is cleared on logout; clients cannot set or spoof it, because the server stores it in a protected per-client field that the infokey lookup returns directly instead of from the player's regular userinfo. KTX reads it to record the player's login name in the match-stats XML and JSON output and to decide whether a player counts as logged in for vote and admin gating (a non-empty value means logged in).
- **ktx `ping:userinfo`**: A client's current connection latency in milliseconds. The server computes this value on demand (averaged round-trip time over recent frames) rather than storing it as a published userinfo field, so a client cannot set it; KTX reads it per player when building the end-of-match ktxstats JSON and writes it as each player's "ping". Connecting/not-yet-spawned clients report 999, a client with no usable timing samples reports 9999, and bots report their configured skill value instead.
- **ktx `tptook:userinfo`**: A client-set bitmask (published via setinfo) that filters which item pickups KTX records as a player's most-recent "took" item for the teamplay "took" report (the tp_msgtook message). The value is a decimal integer whose bits correspond to KTX item types (rocket launcher, lightning gun, armors, ammo, powerups, backpack, etc.); when a player picks up an item, KTX registers it only if its bit is set in this mask. If the key is absent or set to 0, all item types are reported.
- **mvdsv `*admin:serverinfo`**: Holds free-form contact text for the person who runs the server, so players and server-browser tools can see who to reach about the server. The server publishes this whenever its admin-info setting is non-empty and removes the key when that setting is blank; the value is whatever the admin typed (by convention a name and/or email address), with no enforced format.
- **mvdsv `*auth:userinfo`**: Holds a player's verified login (account) name once the server has authenticated them, either against the central account web service or a local account list. Because it is server-stamped and clients cannot set it, it is a trusted identity that other players' clients read to show a login indicator and account name on the scoreboard alongside the chosen nickname. It is empty when the player is not logged in, and is cleared when they log out.
- **mvdsv `*cheats:serverinfo`**: Server-published serverinfo flag that signals whether cheats are enabled for the current session. The server sets it to "ON" when cheats are active -- enabled via the sv_cheats cvar, a devmap load, or the -cheats command-line parameter -- and clears it to empty otherwise; the value is re-evaluated and re-stamped on every map change. The mod reads it to gate cheat-only commands (rejecting them when the flag is empty), and connected clients read it to permit cheat-dependent behavior and to display that cheats are enabled.
- **mvdsv `*csprogsname:serverinfo`**: Names the client-side game-code file (CSQC progs) the server is running -- a filename string, default csprogs.dat -- so each connecting client knows which file to load (downloading it if needed). The server stamps it from its own CSQC progname setting and leaves it blank when no client-side progs file is in use. It travels alongside the matching checksum and byte-size keys that let the client verify the file. Only CSQC-aware clients (FTE) act on it; clients without client-side QuakeC ignore it.
- **mvdsv `*csprogs:serverinfo`**: Holds a checksum of the server's client-side game code (the CSQC `csprogs.dat` program), written as a hex string (e.g. `0x1a2b3c4d`). The server stamps it when CSQC support is compiled in, alongside `*csprogssize` (the file's byte size) and `*csprogsname` (its filename, default `csprogs.dat`). A connecting CSQC-capable client reads this value to confirm it already has the exact matching program and, if not, to download the correct version before joining. All three keys are blank when the server runs no client-side progs.
- **mvdsv `*csprogssize:serverinfo`**: Holds the byte size of the server's CSQC client-side game module (the csprogs.dat file named by sv_csqc_progname), so connecting clients can confirm the copy they download or already have matches the server's. The server stamps this protected key when it loads a CSQC module and leaves it blank on servers that don't use one; it pairs with the module's checksum and filename keys. CSQC is an FTE protocol extension, so only FTE clients act on this key.
- **mvdsv `*flag:userinfo`**: A login flag identifier the server stamps onto a player after a successful account login. The value is supplied by the central login (web auth) service and the server stores it verbatim; a client cannot set it. The client resolves the string against its scoreboard flag image set and renders the matching small icon (conventionally a country/region flag) next to the player on the scoreboard; the string is opaque to the server. It is cleared when the player logs out.
- **mvdsv `*progs:serverinfo`**: A server-stamped serverinfo key identifying the game logic the server is running. For classic QuakeCode mods it holds a numeric checksum of the loaded progs file; for a QVM bytecode mod it holds the checksum of the .qvm image; for a native compiled mod (DLL/shared object) it instead holds the dynamic-library file extension ("so", "dll", or "dylib") rather than a checksum. Clients and the server browser read this value to tell which mod a server is running (for example, a value of "666" flags a Qizmo proxy).
- **mvdsv `*spectator:userinfo`**: Server-stamped flag in a client's userinfo marking that the client is connected as a spectator rather than a participating player. The server sets it (value "1") when someone connects as a spectator, supplies the spectator password, is moved to spectator because the player slots are full, fails the ping requirement, or switches to observing without reconnecting; it is removed when a spectator joins as an active player. Consumers treat the key's presence as the boolean: present means spectator, absent means player.
- **mvdsv `*version:serverinfo`**: Identifies the server software and version that a connected client is talking to. MVDSV stamps this at startup as the server name followed by its version (for example "MVDSV 1.20-dev"); other server implementations populate it differently, so the value also carries the software identity (e.g. clients and mods test it for "MVDSV", "FTE", "qwfwd", or "qtv " prefixes to detect the host type). Clients, server browsers, and the mod read it to learn which server build is running.
- **mvdsv `*z_ext:serverinfo`**: Advertises which optional ZQuake protocol extensions the server supports, as a numeric bitmask that clients read when connecting. Each bit corresponds to one extension (such as server-authoritative game time, view-height stat, pitch limits, on-the-fly join/observe switching, and the VWEP visible-weapon model); the value the server stamps here lists every extension it offers. The features a connection actually uses are the overlap between the bits set here and the bits the client itself advertises, so an extension activates only when both sides claim support for it.
- **mvdsv `*z_ext:userinfo`**: Holds a decimal bitmask of the optional ZQuake protocol extensions that a connecting client implements (reliable jump and the new PM_FLY/PM_SPECTATOR pmove types, the view-height and server-time stats, pitch-limit serverinfo, on-the-fly join/observe switching, the PF_ONGROUND and PF_SOLID playerinfo flags, and VWEP active-weapon models). The client publishes this value in its connect-time userinfo; the server reads it once at connect, records the set of extensions for that client, then removes the key so it does not persist in the stored userinfo. The recorded bits gate which extended features the server later sends to that specific client.
- **mvdsv `epoch:serverinfo`**: Records the wall-clock time at which an MVD demo recording begins, as a Unix timestamp (seconds since 1970). The server writes it into serverinfo when it sends the initial gamestate at recording start, so the value is embedded in the demo stream and lets playback tools and parsers report when the demo was actually captured.
- **mvdsv `map:serverinfo`**: Holds the name of the map the server is currently running, as a bare map name with no path or file extension (for example, dm3). The server stamps this into the global serverinfo string at the end of each level load, so clients and server browsers can read and display the active map.
- **mvdsv `needpass:serverinfo`**: Advisory flag the server publishes to tell clients which passwords it requires. The value is a bitmask: 1 if a player (game) password is set, 2 if a spectator password is set, 4 if a VIP password is set, summed when more than one applies. The key is left empty when no password is set. Client status displays and server browsers read it to show whether a player or spectator password is needed; the value tracks the server's password, spectator_password, and vip_password settings.
- **ktx `di:userinfo`**: Client-set opt-in for KTX's pre-match damage-indicator feed. During warmup/standby (no match in progress), if a player's userinfo carries a nonzero "di", KTX sends that player a per-hit "//ktx di" callback after each hit they land, which the client (ezquake/FTE) renders as an on-screen damage indicator. Value 1 sends a callback only for damage dealt to other players (self-damage excluded); value 2 additionally sends callbacks for self-inflicted damage (e.g. rocket jumps); 0 or absent disables it. There is no corresponding client cvar -- the player publishes this key directly with setinfo, and its meaning is defined entirely by KTX.
- **ktx `ev:userinfo`**: A client-set bitmask that opts the player into KTX's server-event alias callbacks: when a selected event fires, the server stuffs the matching console alias (e.g. on_connect, on_matchstart, on_matchend, on_matchbreak, on_admin, on_unadmin) for the client to execute, with separate spectator/observer variants. Each event is off unless its bit is set: 1 = connect, 4 = match start, 8 = match end, 16 = match break, 128 = granted admin, 256 = lost admin. Bits 2 (weapon switch), 32 (map change), and 64 (deathmatch-mode change) are reserved in the source but not implemented.
- **ktx `fs:userinfo`**: Stores an admin's default target for KTX's force_spec command. An admin sets it with setinfo fs "<value>", where the value is "*" to force-spec all not-ready players, or a player name or numeric player id to target one player (a negative number selects a spectator slot). When an admin runs force_spec without an explicit argument, KTX reads this stored value and uses it as the target; if it is empty, the command prints usage instructions instead.
- **ktx `ti:userinfo`**: Per-client opt-in flag controlling whether KTX sends team-overlay (teaminfo) data to that client during team games. A negative value (conventionally -1) opts the client out entirely; 0 or absent lets KTX auto-detect by client type, where ezQuake clients receive team info automatically; any positive value forces team info on, which is how non-ezQuake clients (e.g. FTE) request it. The client publishes this in its own userinfo; on FTE it is the CVAR_USERINFO cvar "ti" (defaults to 1, "must be 1 in order to receive team information in ktx"), while ezQuake clients omit it and are instead recognized via their reported engine version.
- **ktx `ln:userinfo`**: An optional integer the player sets (setinfo ln) to nudge the vertical position of the "shownick" centerprint popup -- the small info box KTX draws for the player you are pointing at when you use the shownick command. A positive value inserts that many blank lines above the box (pushing it down the screen); a negative value inserts blank lines below it. It has no effect unless shownick is used, and defaults to no offset when unset. (A separate ktpl compatibility key, when set, biases this offset to match KTPro's behaviour.)
- **ktx `lra:userinfo`**: A client-set userinfo value that vertically positions the round-end stats line KTX's Rocket Arena (RA) mode centerprints to a waiting/spectating player -- a one-line summary of the winner's and loser's armor and health. A positive number inserts that many blank lines above the stats line; a negative number inserts that many blank lines below it; zero or unset leaves it flush. It only affects RA stat display and has no effect in other game modes.
- **ktx `lw:userinfo`**: Vertical position offset for the +wp_stats weapon-accuracy centerprint overlay. A positive value pushes the stats block down the screen by inserting that many blank lines before it; a negative value inserts blank lines after it. The player sets this themselves via setinfo (a ktx/ktpro convention, not a client cvar); it pairs with lw_x, which applies a horizontal offset.
- **ktx `lw_x:userinfo`**: Horizontal indent for the +wp_stats weapon-accuracy overlay, the centerprint of per-weapon hit stats KTX shows while a player or spectator is tracking a target. A positive value prepends that many space characters before the stats content; a negative value appends that many spaces after it. Set by the player on their own client (a plain userinfo number, default 0); it is the horizontal companion to the lw key, which shifts the same overlay vertically with blank lines.
- **ktx `nrb:userinfo`**: Non-random bullets toggle. When a player sets this to a nonzero value (typically 1), their shotgun and super-shotgun pellets fire in a fixed, deterministic spread pattern instead of the normal randomized spread, making practice/aim training reproducible. The effect from this key applies only while no match is in progress (it is ignored once a match starts). The deterministic pattern is also forced server-wide whenever yawnmode is active, independent of this key.
