These choices apply to every phase. If any phase needs to deviate, surface a "deviation" section at the top of that phase MD and STOP for operator review -- do not silently override. ## D1. Architecture is locked -- this arc scaffolds and ships, it does not redesign

**Decision:** The v1 pipeline is locked by brainstorm Passes 3-5: **prune** (drop bot/reaction/system via `message_labels.category`, keep chat+link) -> **fence** (Sonnet groups each lull-chunk's messages into topic-coherent threads, `{topic_label, member_indices}`) -> **embed raw member messages** (voyage-4-large) -> **store** `chat_threads` + `thread_messages` -> **hybrid retrieve** (vector primary + FTS via RRF). Cross-session merge, per-thread summary, and the query-time lazy-resolve-mentions loop are dropped/deferred.

**Why:** The calibration probe supplied the architectural evidence (arm D beat arm C 72%, arm B 69%; 0% index-hallucination; 4.38/5 coherence at cap 750; both channels). Pass 3 (index) + Pass 4 (query-time seam) + Pass 5 (decomposition) closed every shape question. Reopening any of them re-litigates settled work.

**Implication:** A phase that finds itself wanting to merge threads, embed a summary instead of raw messages, add a query-time mention-resolve loop, or rank threads by author authority is reopening locked architecture -- STOP and surface, do not implement. The clustering-for-analysis contingency (D13) is the ONLY place merge survives, and only as an offline analysis tool, never retrieval-time.

## D2. Increment 1 (Phase A) is the go/no-go gate -- everything past A is gated on it

**Decision:** Phase A ships a thin end-to-end slice on the already-fenced Feb-Mar 2021 probe slice and proves the production question: **does fenced-thread retrieval beat session-FTS on live queries?** Phases C / buckets-E / D are planned but do NOT run unless A's gate is green. If A underwhelms, the arc stops at A and the negative result is captured.

**Why:** The expensive piece is the full backfill (C). The calibration cleared the architectural bar on a 2% slice; A is the cheap production confirm before paying for the whole corpus (Pass 5.4). Trigger discipline IS the increment-1 gate -- the old "post-deploy query_log evidence" gate is unnecessary.

**Implication:** README marks A as THE gate. Phase C's MD opens with "PRECONDITION: Phase A gate green." Do not plan or kick off C as if it always runs. The gate decision is the operator's (D11).

## D3. Embed raw member messages, not a summary

**Decision:** Each thread's retrieval unit is its **raw member messages concatenated** as `author: content` joined by newline -- byte-identical to the proven arm-D representation at `scripts/calibration/03-embed-and-retrieve.ts:56`. No per-thread summary is generated, stored, or embedded.

**Why:** The 72% win was earned on raw messages; the spine's "embed the summary" was never validated. A summary was a crutch for keyword search; embeddings read raw text directly, and the answering LLM reading the real conversation beats a lossy summary (Pass 3.6). Same logic as no-merge.

**Implication:** `chat_threads` has NO `topic_summary` column -- the spine's `topic_summary TEXT NOT NULL` (`2026-05-03-layer2-thread-reconstruction.md:56`) is dropped. The embedded text == the FTS text == the concatenated raw member messages, stored in a `content` column (D4). `topic_label` (the one-line fence label) is kept as a human-readable display field but is NOT what gets embedded.

## D4. Schema: `chat_threads` + `thread_messages` (the migration shape)

**Decision:** One new append-only migration. Next free number is **021** at planning time, but the qtv-qwfwd sibling arc is in flight and may land 021 first -- the executor takes the next free number and names the file `db/migrations/0NN_layer2_threads.sql`. Shape (mirrors the 004 chat conventions + the 005 concept-chunk vector conventions):

```sql
CREATE TABLE chat_threads (
  id                     BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  thread_key             TEXT NOT NULL UNIQUE,          -- idempotency anchor (D5)
  channel_name           TEXT NOT NULL,
  platform               TEXT NOT NULL CHECK (platform = 'discord'),
  date_range_start       TIMESTAMPTZ NOT NULL,
  date_range_end         TIMESTAMPTZ NOT NULL,
  participant_count      INTEGER NOT NULL,
  participants_json      JSONB,
  message_count          INTEGER NOT NULL,
  topic_label            TEXT NOT NULL,                 -- the one-line fence label (display, NOT embedded)
  content                TEXT NOT NULL,                 -- raw member messages "author: content\n..." (embedded + FTS'd, D3)
  content_tsv            tsvector GENERATED ALWAYS AS (to_tsvector('simple', coalesce(content, ''))) STORED,
  topic_embedding        vector(1024),                  -- voyage-4-large; NULL until the loader fills
  embedding_stale        BOOLEAN NOT NULL DEFAULT FALSE,
  resolution_status      TEXT CHECK (resolution_status IN ('solved','unresolved','informational')),  -- NULLABLE (D7)
  buckets_question       JSONB,                         -- NULLABLE; filled by buckets-E (D8)
  buckets_answer         JSONB,                         -- NULLABLE; filled by buckets-E (D8)
  reconstruction_version TEXT NOT NULL,                 -- model + prompt version tag (D12)
  reconstructed_at       TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX chat_threads_channel_started ON chat_threads(channel_name, date_range_start);
CREATE INDEX chat_threads_status          ON chat_threads(resolution_status);
CREATE INDEX chat_threads_embedding_hnsw  ON chat_threads USING hnsw (topic_embedding vector_cosine_ops);
CREATE INDEX chat_threads_content_tsv_gin ON chat_threads USING GIN (content_tsv);

CREATE TABLE thread_messages (
  thread_id  BIGINT NOT NULL REFERENCES chat_threads(id) ON DELETE CASCADE,
  message_id TEXT   NOT NULL REFERENCES messages(id) ON DELETE CASCADE,
  PRIMARY KEY (thread_id, message_id)
);
CREATE INDEX thread_messages_message ON thread_messages(message_id);
```

**Why:** `'simple'` tsvector config (not `'english'`) because chat is mixed-language -- inherited Arc 1 D7, same call as `messages.content_tsv` (`004_layer2_chat.sql:45`). `vector(1024)` + hnsw + `embedding_stale` mirror `concept_chunks` (`005_layer3_concepts.sql:39-44`). `resolution_status` + buckets ship nullable so increment 1 lands before enrichment (Pass 5.2). `thread_key UNIQUE` is the idempotency anchor (D5). The junction is many-to-many by construction (a bridging meta-comment can belong to two threads) even though v1's fencer partitions (R8).

**Implication:** `sessions` / `session_search` / `session_references` (004) stay -- threads layer on top; sessions remain raw timestamp grouping for adjacent-context. Update `SCHEMA.md` in the same commit as the migration. Never edit an applied migration (append-only). JSONB columns receive JS values, not pre-stringified JSON (D12).

## D5. Idempotency: deterministic `thread_key`, delete-scope-then-insert

**Decision:** Every thread gets a deterministic key `thread_key = "{channel_name}:{reconstruction_version}:{chunk_id}:{thread_index}"`, UNIQUE. A backfill batch (C) is scoped to a (channel, year) span at a given `reconstruction_version`; **re-running a batch DELETEs all `chat_threads` in that scope (CASCADE drops `thread_messages`) then re-inserts.** A re-run produces identical state -- never duplicates. The loader's keying logic is a SHARED helper used by both Phase A and Phase C.

**Why:** HARD requirement (handoff + Pass 3.4). Precedent in-repo: `concept_chunks` UNIQUE(concept_slug, chunk_index) delete-and-rebuild per slug; `change_events` UNIQUE for diff-pipeline idempotency (Arc 1 F6). A deterministic key tied to chunk + thread position survives re-runs without a content hash.

**Implication:** The batch DELETE predicate MUST exactly cover what its INSERT writes (R5) -- express the scope as `WHERE channel_name = $1 AND reconstruction_version = $2 AND date_range_start >= $3 AND date_range_start < $4` (or a `thread_key LIKE` prefix), and verify it matches the key construction. `reconstruction_version` is part of the key so a re-fence at a new model/prompt version coexists with the old until explicitly superseded.

### Amendment 2026-06-06 (Phase C prep execution) -- production load uses version-AGNOSTIC range-delete (supersede), not version-scoped

**Do not revert.** The production loader (`scripts/load-chat/thread-loader-core.ts`, shared by both Phase A's `load-threads.ts` and Phase C's `backfill-batch.ts`) deletes by **(channel, date_range_start window) ONLY -- NOT scoped by reconstruction_version**. Rationale: the retrieval index wants exactly ONE version per (channel, date) range. Phase A's `fence-sonnet-v1` threads are increment-1 probe scaffolding (cap 750 / probe gap) to be REPLACED by production `fence-sonnet-v2` (12h / 1500), not to coexist. A version-agnostic range-delete makes the reset-day full-year-2021 v2 batch automatically supersede A's v1 (the "fold #1" supersede the orchestrator flagged at the prep checkpoint) with no orphaned v1 rows. Idempotency is preserved: re-running a batch deletes its date range (including what it just inserted) then re-inserts identically; `thread_key` UNIQUE is the tie-breaker. The version-scoped `batchScopeClause` in `thread-key.ts` REMAINS available for any future safe-coexistence migration, but the production load deliberately does NOT use it. This supersedes D5's original implication (version-scoped delete + "coexists until explicitly superseded") for the production path. Verified in prep: a synthetic prior-version row was cleared by reload while v2 stayed intact (fold #1 PASS).

**At-scale confirmation 2026-06-09 (RUN #helpdesk 2021 supersede) -- mechanism proven on real data.** Loading full-year v2 #helpdesk-2021 (1346 threads) cleared all 374 real v1 probe rows in the (#helpdesk, [2021,2022)) scope (v1 #helpdesk 374->0, 0 residue) while leaving the v2 sibling years (#helpdesk 2020/2022/2026 = 715/1015/373) and the other channel's v1 (#quakeworld 634) untouched. Orchestrator cold-verified against the dev DB: total 3178->4150 (-374 v1 +1346 v2), all invariants clean (0 null/stale/collision/non-year-scoped/orphan). The synthetic 1-row prep proof now has a 374-row at-scale confirmation. The one remaining v1 supersede -- **#quakeworld 2021** (634 v1 probe rows) -- is governed by this same mechanism and gets the same orchestrator cold-verify when its batch runs.

## D6. Hybrid retrieval rewire -- copy `search_entities` exactly

**Decision:** `search_solved_issues` becomes vector-primary + FTS-secondary fused via `reciprocalRankFusion` (`shared/rrf.ts`, k=60), the exact shape of `serve/mcp/src/tools/search-entities.ts`: embed the query with `voyage-4-lite` (`input_type: 'query'`), kNN on `topic_embedding` (`<=> $vec::vector`), tsvector candidates on `content_tsv` (`websearch_to_tsquery('simple', ...)`), RRF-fuse on thread id, hydrate top hits' member messages via `thread_messages`. Voyage failure -> lexical-only degraded path (no throw), logged to `embedding_api_log`.

**Why:** Arm A (pure FTS) whiffed `[NO HIT]` on 32/36 symptom queries -- vector MUST be primary. FTS is retained as a cheap secondary for literal-name queries (a typed cvar appears verbatim in the thread text). `search_entities` is the proven in-repo hybrid pattern; consistency over reinvention (Pass 3.5).

**Implication:** `match_quality` moves from `ts_rank` thresholds (`L2_TS_RANK_*`) to RRF-score thresholds. Use new env vars `L2_RRF_STRONG_THRESHOLD` / `L2_RRF_WEAK_THRESHOLD`, **provisionally defaulted to the `search_entities` values (STRONG=0.02, WEAK=0.005)** until Phase D recalibrates against fenced-thread retrieval. The return type changes from `SessionHit` to a thread-shaped hit (thread identity + hydrated member messages); `serve/mcp/src/types.ts`, the orientation blob (`serve/mcp/src/orientation.ts`), and `API_CONTRACTS.md` (drift #1) update in the SAME commit (Discovery contract). The old `session_search` FTS path is retired as the retrieval unit; the table stays for adjacent-context.

## D7. `resolution_status` rides Phase C as a passenger with a batch-1 kill-switch

**Decision:** Phase C's fence prompt optionally also emits `resolution_status` (`solved` / `unresolved` / `informational`) per thread. Validated on **batch 1**: if fencing stays clean (0% index-hallucination + coherence held -- the existing backfill backstop), keep it riding C. If emitting it perturbs fencing at all, drop it from the fence prompt and run a separate per-thread resolution pass later. `resolution_status` is per-conversation LOCAL truth, never cross-conversation synthesis.

**Why:** The label needs the conversation, and the fence pass already holds it in context (Pass 5). Three fixed values = stable rubric = low re-run risk (unlike buckets, D8). It is operator-side metadata (authoring backlog / regression benchmark), not a retrieval signal.

**Implication:** Phase A promotes the probe's threads, which were fenced WITHOUT `resolution_status` -- A writes it NULL (R1). The fence schema in C gains an optional `resolution_status` per thread. C's batch-1 task includes the explicit kill-switch comparison (R6). NEVER a retrieval filter -- all threads stay in the index regardless of status (survivorship-bias lesson; `2026-05-03-layer2-thread-reconstruction.md:267`).

## D8. buckets-E is decoupled from fencing and re-runnable

**Decision:** Bucket labeling (`buckets_question` / `buckets_answer`, the 9-bucket taxonomy) is its OWN pass over the fixed threads, AFTER backfill -- a Workflow labeling fan-out that reads `chat_threads` and UPDATEs the bucket columns. Re-runnable over fixed threads without re-fencing. Idempotent UPDATE (re-run overwrites).

**Why:** FAQ-discovery (mining tagged threads for which concept-notes to author) is a primary payoff (Pass 5 vision framing), but the taxonomy is still discovered empirically and will evolve. Coupling it to the expensive fence pass would force a re-fence on every taxonomy tweak. Cheap (headline-readable) and re-runnable keeps taxonomy iteration free.

**Implication:** The 9 buckets: `engine-config` / `engine-content` / `visual-customization` / `system` / `hardware` / `peripherals` / `network` / `server-side` / `community` (spine + `2026-05-03-layer3-multidomain-bucket-framework.md`). Multi-tag. buckets-E is gated post-C; it does not touch the fence pass. Cross-domain threads (question-buckets != answer-buckets) are the L3 concept-note-candidate signal.

## D9. Cost is quota-paced, not dollar-budgeted; LLM work routes through Workflow

**Decision:** There is no `ANTHROPIC_API_KEY`. All LLM fan-out (fence in B / C, labeling in buckets-E) routes through the **Workflow tool** as **Sonnet** subagents, with the proven recipe: `model='sonnet'`, `CONC=5`, paced waves (~2s), an 8s recovery+retry pass, and HONEST success/fail counts in the return value (no silent `.catch(() => null)`). 1-2 batches per session in C, quota-paced. The deterministic spine (DB, Voyage embed, math, aggregation) stays as Bun scripts in the main session.

**Why:** Max subscription, no API key (`reference_max_subscription_no_api_key`). A 251-agent Opus burst trips a SHARED account-wide throttle and starves other terminals (`reference_workflow_rate_limit_and_args`). The probe proved conc-5 Sonnet held clean at 251 agents over 32 min, coexisting with another terminal. `scripts/calibration/wf-a-fence-queries.js` is the reference recipe.

**Implication:** `args` reaches a workflow script as a JSON string -- normalize `const A = typeof args === 'string' ? JSON.parse(args) : (args ?? {})` at the top of every workflow script. Backfill scale (B's cap is the dial): whole backfill ~650-750 agents @ cap 750, ~150-200 @ cap 3000; biggest single batch ~80 agents (qw-2018 @ 750). Voyage embedding (small) is the only real dollar cost. Trial a small wave before a full batch to confirm the config clears the throttle.

### Amendment 2026-06-06 (Phase B execution) -- D9 backfill estimate corrected ~25x; swept dial inverts cap -> gap

**Do not revert.** Phase B's read-only gap-sweep, run over the FULL 728k-message corpus (a direct measurement, not an extrapolation), found D9's "~650-750 agents @ cap 750" badly wrong: it divided messages by the cap and ignored that lull-chunking cuts at quiet gaps, so the cap almost never binds. At the planned **3h gap / cap 750 the real backfill is 18,365 agents** (median bite 9 messages -- the 3h gap shatters the corpus into ~18k scraps and splits overnight Q&A across the gaps). The calibration probe's 221 chunks for 2 months x 2 channels extrapolates to ~18k for the full corpus, confirming the measurement.

**Corrected decision:** the swept dial is the **lull gap**, not the chunk cap. The cap's proven-safe value is **750**, but that is a tested FLOOR, not a measured ceiling: 0% hallucination AT 750 means 750 is safe, not that it is the maximum (operator catch 2026-06-06). Measured: at ~59 chars/message a 750-msg chunk is only ~15-20k tokens, under 10% of Sonnet's ~200k context; the physical wall is roughly ~5-9k messages (input context, pulled down by the assignment the fencer must emit), so the true quality ceiling is unknown but well above 750. The cap chops any over-cap bite into <=cap-message chunks, so each agent's per-call load is bounded by the cap (proven clean at 750); raising the gap only moves where cuts fall, it does not make any single agent's job harder. **Backfill operating point: 12h gap / cap 750 -> ~4,058 agents** (78% fewer than 3h), median bite 42. Measured sweep:

| gap | agents @cap750 | vs 3h | median bite | max bite | note |
|---|---|---|---|---|---|
| 3h | 18,365 | 100% | 9 | 2,115 | original plan; Q&A split overnight |
| 6h | 9,495 | 52% | 22 | 4,139 | |
| **12h** | **4,058** | **22%** | **42** | **22,673** | **knee -- chosen operating point** |
| 24h | 1,778 | 10% | 77 | 62,125 | peak year = one 62k blob, 698 forced cuts -- REJECTED (loses natural boundaries) |
| 48h | 1,189 | 6% | 107 | 62,125 | diminishing; mostly cap-chopping |

**Residual (the quantified catch):** at 12h, ~400 of the ~4,058 cuts are cap-FORCED mid-marathon rather than lull-bounded. Far fewer bad cuts than 3h's pervasive overnight-splitting, but NOT zero. So Phase B's quality gate MUST fence a 12h sample that INCLUDES at least one cap-forced (marathon-slice) chunk and confirm coherence ~4 there -- forced cuts are the one new failure mode the gap-raise introduces. **Cap-sweep is a REAL sub-task (operator catch 2026-06-06), not optional polish:** since 750 is a floor not a ceiling, sweep the cap UP -- 1500 / 3000 / 6000, toward the ~5-9k physical wall -- on the biggest 12h bites, measuring BOTH index-hallucination AND coherence (a bigger chunk may keep indices valid yet start lumping unrelated conversations, which shows in coherence, not hallucination); take the largest size holding 0% hallucination + coherence ~4. A higher cap shrinks the ~400 forced cuts and drops the agent count further; the 62k peak-year blobs always need some cap (they exceed the physical wall). 12h finally makes this testable (34 bites >=3000; 3h produced zero). Embedding is per-thread, so cap changes are fencing-only and cheap to test.

**Cap-sweep RESULT (2026-06-06, orchestrator-ratified):** swept 750/1500/2500 on the worst-case bite (#quakeworld 2017, 22,673 msgs, all cap-forced marathon-slices -- the hardest sample). 0% index-hallucination at every cap; coherence non-regressing (3.6 / 3.4 / 3.6 vs the same-harness 750 control -- the absolute ~3.5 reflects the worst-case sample, not a cap effect, so "coherence ~4" holds only as NON-REGRESSION, not in absolute terms). The one cap-monotonic degradation is partition cleanliness: dup-assignment 0% / 0.44% / 1.85%, coverage 100% / 98.9% / 98.3%. **Production cap = 1500.** It clears the hard gates, keeps the partition essentially intact (<1% dup), and halves forced cuts vs 750 (139 vs 401) at ~the same agent cost. 2500 (the literal "largest passing") is REJECTED: its ~2% agent saving is not worth 4x the dup rate -- "largest passing" is superseded by "largest CLEAN passing". Phase C = **~3,796 agents** at cap 1500 (750->4,058 / 1500->3,796 / 2500->3,717: the cap is a near-non-dial, ~8% across the range; the 12h gap was the cost lever, the cap is a cleanliness lever trimming forced cuts on the ~34 bites >=3000). The 6000 model-ceiling probe is DECLINED (R13 makes it moot). Minor residual: ~1% coverage drop on worst-case forced-marathon chunks (logged per-batch; natural chunks are 100%) -- Phase C tracks coverage per batch, so it is not silent loss.

**R13 supersedes the ~5-9k context-wall estimate above:** the real chunk ceiling is the fence-agent's 256KB Read cap (~2,700 msgs), LOWER than Sonnet's context. cap 1500 is comfortably under; `backfill-batch.ts` mirrors `sweep-prep.ts`'s <256KB write-time guard. Do not raise the cap above ~2,700 without multi-file chunk delivery.

**Architecture check:** this stays inside D1. The lull gap is a parameter of the chunking step that FEEDS the fencer; it does not touch the locked-out items (retrieval-time merge, embedded summary, query-time lazy-resolve, author-authority ranking). The pipeline stages are unchanged.

**Phase C impact:** C must budget ~4,058 agents at 12h (NOT D9's ~650-750), and re-fence the 2021 slice under the production gap + `reconstruction_version` for consistency (C's open-question resolves to re-fence). Watch a year-boundary straddle in `batchScopeClause` -- a 12h+ bite can cross Dec 31 -> Jan 1; scope C's idempotent DELETE so a straddling thread is covered exactly once. The orchestrator augments C's executor prompt with this corrected scale at kickoff.

**Incremental-update note (future arc, NOT this one):** backfill maximizes the gap (12h) for cheapness; daily incremental pulls want a TIGHTER gap (~6h on busy channels) so a frequent safe boundary exists (at 12h, peak #quakeworld has a clean lull only ~every 2 weeks). The two gaps need not match.
