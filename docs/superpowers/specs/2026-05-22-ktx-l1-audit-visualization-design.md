# KTX L1 audit visualization + LLM-derived categorization -- design (2026-05-22)

**Status:** Design complete; pending operator review, then writing-plans for the implementation plan.
**Trigger:** Operator wants to visually audit the 618 D20-rewritten KTX cvar+command descriptions shipped 2026-05-21 in the format-unify arc. The data is DB-resident; no human-browsable surface exists today without writing SQL.
**Supersedes:** Visualization candidate (2) in `docs/superpowers/parking/2026-05-21-ktx-mvdsv-followup-triage-handoff.md` -- the handoff's premise was wrong (`apps/qw-oracle/reviews/` doesn't exist; the actual `apps/qw-oracle/docs/reviews/` holds markdown reports, not HTML). This spec defines the real HTML probe and the categorization substrate that makes it (and future docs surfaces) useful.

---

## Summary

A single-page HTML catalog at `apps/qw-oracle/docs/reviews/<DATE>-ktx-l1-catalog.html` that renders every KTX cvar and command from Layer 1 with grouped, collapsible navigation. Sticky left-rail TOC, function-based category groups, two-tier collapse (group -> entity card -> full description + audit trail), filter box for substring search, dark theme with Quake-flavored amber accents. Generated by `apps/qw-oracle/scripts/build-l1-audit-catalog.ts` from Postgres -- idempotent, regenerable, byte-stable.

The categorization underneath is the substrate that makes it work and the reason this is more than a one-off probe. KTX has no in-source categorization mechanism (unlike ezQuake's `Cvar_SetCurrentGroup`, which the L1 extractor captures as `cvar_versions.group_name_in_source` at 85% coverage for ezQuake). For KTX -- and later for MVDSV / QWCL, all at 0% coverage of source-truth groups -- we synthesize a function-based category per entity via an LLM pass (Sonnet medium, sub-agent fan-out) and persist it in a new column `category_inferred` alongside a provenance sibling `category_inferred_origin`. Same shape as `description_origin`. Three consumers benefit: oracle MCP (filter by category), the audit HTML this spec defines, and any future docs surface (wiki / ezquake.com-style docs site / slipgate UI).

---

## Goals

1. **Audit-shape visualization.** Operator can scan all 618 KTX entities, read the D20 prose, judge the shape of what shipped, and form an opinion on whether MVDSV should mirror the workflow as-is or with adjustments.
2. **Future-proof substrate.** The categorization column persists in L1; future consumers (MCP queries, wiki pages, docs site, slipgate UI) read it without re-doing the work.
3. **MVDSV transferability.** Same script, same column, same pipeline pattern works against MVDSV when its describe-fill ships. No KTX-specific assumptions baked in.
4. **Idempotent + regenerable.** Re-running any step produces byte-identical output. The HTML can be regenerated after re-embed, after a category re-tag, or whenever a stale snapshot is suspected.

## Out of scope

- **ezQuake categorization.** ezQuake's source already carries `Cvar_SetCurrentGroup` calls at 85% coverage. No LLM pass needed; `group_name_in_source` is sufficient.
- **Cross-engine normalized taxonomy.** Each engine gets its own category list (KTX now, MVDSV later). Unified "Admin" across all engines is deferrable to a future docs-site arc.
- **Public hosting.** The HTML is a local file in `apps/qw-oracle/docs/reviews/` for now. Public docs-site hosting is a separate arc.
- **MediaWiki category sync.** The `category_inferred` column COULD drive MediaWiki categories later, but the qwiki Phase 5+ arcs decide how to consume it. Not built here.
- **Auto-regenerate on DB change.** Manual CLI only. Docs-check / docs-watch integration is a future polish item.
- **MVDSV execution.** Schema and script are MVDSV-ready; the MVDSV category list and apply ledger ship with MVDSV's describe-fill arc, not here.
- **Search highlighting / per-entity deep links / URL fragments.** v0 stays minimal -- substring filter + scroll. Polish deferrable.

## Background

The describe-fill arc (`docs/superpowers/plans/2026-05-16-ktx-mvdsv-l1-describe-fill/`) shipped 607 D20-template KTX cvar+command descriptions on 2026-05-21 (arc-history retrospective, tag `arc-ktx-format-unify-shipped`, decisions.md D20+D21). All entities now carry user-facing prose plus an audit trail in `description_reasoning`. The schema supports the two-track separation. What's missing is a way for the operator to **see** what shipped without writing SQL queries.

Three grouping axes were probed and three failed cleanly:
- **Name prefix** -- 144 of ~260 cvars and 312 of ~358 commands fall into generic "other" buckets. Only ~120 of ~620 entities cluster into meaningful prefix subgroups (k_vp_*, k_fbskill_*, k_race*, _k_*, k_midair*). Weak.
- **Source file** -- 222 of 260 cvars live in `src/world.c`, 319 of 358 commands in `src/commands.c`. Dead.
- **`gameplay_mechanics.mode_default`** -- 317 rows exist but `props_json` stores initstring references and comments, not cvar canonical_id pointers. The mode->cvar linkage is not in the schema today.

ezQuake's mechanism is `Cvar_SetCurrentGroup(CVAR_GROUP_X)` -- a C macro called before blocks of `Cvar_Register()` calls that the libclang extractor captures into `cvar_versions.group_name_in_source`. ezQuake covers it at 34106/40120 rows (85%); KTX, MVDSV, QWCL all at 0%. KTX has no in-engine variable browser, so no equivalent source-truth mechanism exists or is needed. The categorization KTX needs is **function-based for downstream consumers (oracle, docs site, wiki)**, not menu-organized for an engine UI. Synthesizing it via LLM is the natural path.

The shape of the synthesized taxonomy mirrors ezquake.com/docs's coarser top-level categories (Features / Graphics / Reference / Settings reference / Misc) -- ~10-15 function-based groups -- rather than ezQuake's ~50 fine-grained source `SetCurrentGroup` taxonomy. The docs-site taxonomy is what serves browsing humans; the source taxonomy serves in-engine menu rendering. KTX needs the former, not the latter.

## Locked decisions

These are settled by the brainstorm and should not be re-litigated:

1. **Per-row shape** = D20 prose (description) + optional metadata strip (verdict / origin / confidence / anchor / source_ref) + audit trail (description_reasoning when non-null). Collapsed state shows name + type badge + char count + first paragraph of description. Click expands.
2. **Two-tier collapse** = group section -> entity card. Groups collapsed by default. Entity cards inside an expanded group are also collapsed by default (first paragraph visible). Click entity card to see full description + metadata + audit trail.
3. **Grouping = LLM-derived function-based categories.** ~13 per engine, locked during calibration. Stored in new column `category_inferred` (TEXT) on `cvar_versions` and `command_versions`. Provenance sibling `category_inferred_origin` (TEXT) carries `{model}|{prompt_version}` tag (matches `description_origin` convention).
4. **Macro layout = single scrolling page + sticky left-rail TOC + top filter box.** No per-category pages, no three-pane app shell. Audit-optimized: minimum clicks between operator and prose.
5. **Visual style = dark theme + amber accent (#ffb454) + mono entity names in light blue (#9cdcfe) + sans-serif prose.** Self-contained HTML, vanilla JS, no external CSS/JS. Aesthetic: "VS Code dark with a Quake accent."
6. **Per-engine categories, not cross-engine normalized.** KTX gets KTX-tuned categories. MVDSV gets MVDSV-tuned categories when its describe-fill ships. Unified taxonomy deferred to a future unified-docs-site arc.
7. **ezQuake stays with `group_name_in_source`** -- no LLM pass for ezQuake. Its source-truth groups are sufficient.

## Design

### Page anatomy

Three regions, top to bottom:

**Top bar** (full width, sticky)
- Title: "KTX L1 audit catalog"
- Subtitle: entity count + project + anchor SHA + generation timestamp
- Filter input: live substring match (case-insensitive) against `name + first paragraph of description`. As the operator types, non-matching entity cards hide and TOC counts re-tally to reflect filtered set.

**Sticky left rail** (occupies ~25-30% of viewport width, scrolls independently)
- TOC: each category listed with entity count and a click-to-jump anchor.
- Filter mirrors the top bar's behavior on the TOC counts.
- Visual indicator of which category is currently in view (scroll-spy, optional polish).

**Main scroll column** (remaining width)
- Category sections stacked top to bottom. Each section starts with a header bar (category name + count + chevron). Collapsed by default.
- Click the header to expand the section -- reveals the entity cards inside.
- Within an expanded category, entity cards are stacked, each also collapsed by default showing only `name + type badge + char count + first paragraph of description`.
- Click an entity card to expand it -- reveals the full description, the metadata strip, and the audit trail.

**Per entity card -- collapsed state:**
```
+ k_admins                                       cvar . 358c
  Master toggle for the KTX admin system. When disabled, all admin-related
  commands print "NO admins on this server!" and bail.
```

**Per entity card -- expanded state:**
```
- k_admins                                       cvar . 358c . anchor
  Master toggle for the KTX admin system. When disabled, all admin-related
  commands print "NO admins on this server!" and bail; admins cannot be
  designated or take admin actions.

  0 = admin system unavailable on the server.
  1 = admin system enabled (commands like /admin, /elect, etc. work).

  Default: 0.
  Set by: server config only.

  --- metadata ----------------------------------------------------
  verdict: AFFIRM     origin: synthesized     confidence: HIGH
  anchor: 1.47-2-g67253dc                source: src/world.c:1442

  --- audit trail (description_reasoning) -------------------------
  (anchor row -- no reasoning; D20 template authored by hand)
```

**Flag badges** (top-right of each card, small subtle tags) appear when relevant:
- `anchor` -- the 11 D20 template anchors (NULL reasoning by design)
- `See also` -- description carries a See-also pointer
- `NULL reasoning` -- one of the 16 NULL-reasoning rows (11 anchors + 5 lean-v2 calibration)

### Categorization pipeline (five steps)

Mirrors the format-unify shape (decisions.md D21 mechanism).

**Step 1. Schema migration.**
- `db/migrations/<NNN>_l1_inferred_category.sql` (next available migration ordinal -- DERIVED at execution time, not frozen here; per `feedback_cross_phase_audit_shared_file_drift`).
- Adds `category_inferred TEXT` (nullable, no CHECK) to `cvar_versions` and `command_versions`.
- Adds `category_inferred_origin TEXT` (nullable, no CHECK) as the provenance sibling -- format `{model}|{prompt_version}`, e.g. `claude-sonnet-4-6|b6-categorize-v1`.
- `SCHEMA.md` updated in the same commit (no integer version counter -- retired with Arc 1; the doc tracks current state, the migration files are the append-only audit trail).
- F1 probe extended: `F1.runtime_fidelity_shape` adds an assertion that `category_inferred IS NULL OR category_inferred_origin IS NOT NULL` (provenance integrity), and a separate floor probe for KTX `category_inferred` non-null coverage (snapshotted after fan-out).

**Step 2. Sub-agent prompt + calibration.**
- `docs/superpowers/plans/2026-05-22-ktx-l1-categorize/b6-categorize-prompt.md` -- the locked sub-agent brief, mirroring `b5-format-unify-prompt.md` structure.
- Pre-reads: this spec + the strawman category list + the format-unify D20 template (so the sub-agent understands what the description prose looks like).
- Per-row task: read `name + description + description_reasoning + source_file + source_line` (joined from `cvar_versions` / `command_versions`) for each canonical_id in the batch, emit ONE category from the locked list OR a structured "new category needed: <name> -- reason: <one line>" if no listed category fits OR a HALT for genuinely uncategorizable rows (broken / malformed / unclear).
- Output ledger shape (per row): `B6-RESULT | <canonical_id> | CATEGORIZED | category=<value> | confidence=<HIGH|MED|LOW>` plus a per-row narrative block with the canonical_id, chosen category, and 1-2 sentence reasoning. HALT rows use `B6-RESULT | <canonical_id> | HALT-<reason> | residue: <one-line>` with a per-row block explaining what blocked categorization and a recommendation (hand-assign / defer / escalate).
- Calibration ledger: `docs/superpowers/plans/2026-05-22-ktx-l1-categorize/b6-categorize-calibration.md` -- 30-row sample (spanning anchors / non-anchors / various lengths / various entity types). Operator reviews the ledger; if any "new category needed" entries appear, operator decides to fold or split. Category list LOCKED post-calibration.

**Step 3. Fan-out.**
- ~30 batches of ~20 entities each. Skip-list = the calibration 30. Total ~590 entities post-calibration.
- 4 waves of ~8 batches dispatched in parallel (same shape as format-unify -- wave 1 of 8, spot-check, wave 2, spot-check, etc.).
- Each batch produces `docs/superpowers/plans/2026-05-22-ktx-l1-categorize/b6-categorize-batch-NN.md` ledger.

**Step 4. Apply.**
- `apps/qw-oracle/scripts/describe-fill/apply-l1-category.py` -- clone of `apply-l1-format-unify.py`, edited to write `category_inferred` + `category_inferred_origin` instead of `description`.
- Glob: `b6-categorize-*.md` in the plan dir.
- Idempotent UPDATE statements; defensive defaults (only write columns explicitly present in the ledger; never null out an existing value).
- Single transaction; ~620 UPDATEs.

**Step 5. Generate HTML.**
- `apps/qw-oracle/scripts/build-l1-audit-catalog.ts` -- Bun/TypeScript, per project convention (`apps/qw-oracle/CLAUDE.md` "Always-on rules").
- CLI: `bun apps/qw-oracle/scripts/build-l1-audit-catalog.ts --project ktx [--output PATH]`.
- Default output: `apps/qw-oracle/docs/reviews/<TODAY-DATE>-ktx-l1-catalog.html`.
- Reads from `entities` joined to per-type version tables (`cvar_versions` for cvars, `command_versions` for commands) to assemble per-entity records.
- Emits one self-contained HTML file -- inline CSS, inline JS for collapse + filter behavior. No external assets, no build pipeline, no framework.
- Idempotent: same DB state -> byte-identical HTML.
- Header shows: project, entity count, anchor SHA (most common `description_anchor_version` value), generation timestamp (UTC), build SHA of the script source.
- **Coverage guard:** the generator pre-checks `SELECT count(*) FROM ... WHERE project='ktx' AND type IN ('cvar','command') AND category_inferred IS NULL`. If non-zero, it errors out and prints the offending canonical_ids (do not silently emit an "Uncategorized" group -- the whole point of the artifact is that everything is categorized).

### Generator script details

**Data fetching (single query per type, joined for completeness):**
```sql
-- Cvars
SELECT e.canonical_id, e.name, e.type, e.description, e.description_reasoning,
       cv.category_inferred, cv.category_inferred_origin,
       e.description_verdict, e.description_origin, e.description_confidence,
       e.description_anchor_version, cv.source_file, cv.source_line
FROM entities e
JOIN cvar_versions cv ON cv.entity_id = e.id
WHERE e.project = 'ktx' AND e.type = 'cvar'
ORDER BY cv.category_inferred NULLS LAST, e.name;
-- Same shape for commands joined to command_versions.
```

**HTML structure (per-entity card markup -- pseudocode):**
```html
<div class="card" data-canonical-id="..." data-category="...">
  <div class="card-header" onclick="toggleCard(this)">
    <code class="entity-name">{name}</code>
    <div class="badges">{type, char-count, anchor?, See-also?, NULL-reasoning?}</div>
    <div class="first-para">{first-paragraph-of-description}</div>
  </div>
  <div class="card-body" hidden>
    <pre class="description">{full-description-D20-line-breaks-preserved}</pre>
    <div class="metadata-strip">{verdict, origin, confidence, anchor, source_ref}</div>
    <div class="audit-trail">{description_reasoning OR "(anchor row -- no reasoning)"}</div>
  </div>
</div>
```

**Inline JS (~50 lines vanilla):**
- `toggleCard(el)` -- toggles `hidden` on the `.card-body` and flips the chevron.
- `toggleGroup(el)` -- toggles a group section's collapsed/expanded state.
- `filter(input)` -- live filter on a single text input. For each `.card`, set `hidden` based on whether `name + first-paragraph` (data attributes) contain the substring (case-insensitive). Recompute group counts in the TOC.

**Performance budget:** ~620 cards x ~250-500 bytes each = ~200-300KB HTML. Trivial for modern browsers even fully expanded.

### Visual style

- Dark theme: bg `#1a1a1a`, panels `#1f1f1f`, borders `#333` (collapsed) / `#5a4a2a` (expanded accent).
- Amber accent `#ffb454` for active markers, group headers, chevrons.
- Entity names: mono (`ui-monospace, monospace`), light blue `#9cdcfe`.
- Description prose: sans-serif (`ui-sans-serif, system-ui`), off-white `#ddd`, line-height 1.5, `white-space: pre-wrap` to preserve D20 line breaks.
- Metadata + badges: dimmed gray `#777` / `#888`, smaller font (~11px).
- Audit trail: italic, slightly dimmer `#aaa`, file:line refs highlighted in `#9cdcfe`.
- No light mode toggle in v0.

## Strawman category list (KTX)

Locked during calibration; this is the seed:

1. **Admin & permissions** (k_admins, admin tier cvars, rcon, ban management)
2. **Voting** (k_vp_* family, vote policy, vote thresholds)
3. **Match flow** (prewar, ready, restart, break, timer, match-state transitions)
4. **Gameplay rules** (weapon balance, item respawn, damage tuning -- not mode-specific)
5. **Mode selection** (commands that switch the active mode: clan_arena, wipeout, midair, dmm <N>, instagib, bloodfest, lgc)
6. **Mode-scoped knobs** (cvars whose effect is scoped to one specific mode: k_dmm4_*, k_ca*, k_wp*, k_lgc*, k_666*, k_midair*, k_bf*)
7. **Frogbot** (skill, behavior, waypoints: k_fb*, k_fbskill_*, fb commands)
8. **Race** (race mode cvars + commands -- self-contained ecosystem)
9. **Demo & spectator** (recording, replay, spec controls, broadcast policy)
10. **Spectator chat & visibility** (k_spectalk family -- surfaced in Session #9)
11. **Scoring & stats** (frag rules, stat tracking, end-of-match data)
12. **Server config & network** (rates, slots, hostname, MOTD, sv_* server-side)
13. **Internal state** (`_k_*` -- KTX engine internals, not user-tunable)

Calibration may surface the need to split or merge. The category list is LOCKED after calibration; fan-out enforces the locked set.

## MVDSV reuse path

The schema column lives on shared tables (`cvar_versions` / `command_versions`), so MVDSV gets the column for free. When MVDSV's describe-fill arc ships, the categorization mini-arc for MVDSV reuses:

- Same `apply-l1-category.py` -- runs against a different ledger dir (`docs/superpowers/plans/<DATE>-mvdsv-l1-categorize/`).
- Same `build-l1-audit-catalog.ts --project mvdsv` -- different SQL filter, same generator.
- New `b6-categorize-prompt.md` clone tuned for MVDSV (different strawman category list -- probably leaner: server config + network + broadcasts + MOTD + admin, fewer mode tunables).
- New calibration ledger + fan-out ledgers under MVDSV's plan dir.

ezQuake stays out -- its `group_name_in_source` is the source-truth signal and adding a redundant LLM-derived signal would conflict without benefit.

## Open questions (deferred to plan-time or post-implementation)

These don't block design sign-off. They surface during writing-plans or after the artifact ships.

- **Scroll-spy on the TOC** -- live highlight of which category is currently in view. Polish item, not v0.
- **URL fragment deep-links** -- `#category-admin` / `#entity-k_admins` for sharing specific views. v0 nice-to-have if cheap; otherwise v1.
- **Filter highlighting** -- highlight the matched substring in name and description prose. v0 nice-to-have if cheap.
- **Per-card "copy as markdown"** action -- emit the entity's full record (name + description + reasoning + metadata) as markdown to clipboard. Useful for the upstream PR workflow. Plan-time decision.
- **Multi-version comparison** -- show how a cvar changed across anchor versions. Out of v0 scope; future arc if needed.
- **Sort within a group** -- alphabetical by name is the default. Could add "by char count" / "by anchor version" / "by NULL-reasoning first" toggles. v0 keeps alphabetical only.
- **F1 floor for `category_inferred` coverage** -- snapshotted at first successful fan-out. Calibration set + fan-out apply = the floor. Below the floor without `--force` -> regression. Plan-time defines the exact numeric.
