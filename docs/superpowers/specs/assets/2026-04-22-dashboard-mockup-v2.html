cvar

User-tunable engine variable. The knob the player turns.
What it entails
A named value the engine reads and the player can set. Covers every adjustable aspect of the client: graphics (gl_fog), input (sensitivity), gameplay toggles (cl_smartjump), teamplay behaviour (tp_pickup), HUD layout. The schema stores name, default, type (int/float/string/enum), description, flag bits (CVAR_ARCHIVE, CVAR_USERINFO, etc.), enum values where applicable, and the source file + line it was declared at.
Why we extract it
cvars are the primary surface a player tunes. A config file is 95% cvar assignments. Any consumer that wants to understand, visualize, or validate a config needs the cvar definitions - types, defaults, valid enum values. Without this table, seta crosshair 3 is just text.
Example
sensitivity 3.0, cl_crossx -2, gl_fog 1. In-engine: CVAR_REGISTER(&sensitivity, ...)
Consumers
slipgate ConfigViewer config linters (future) chatbot Q&A cvar diff tools
-> Schema: SCHEMA.md#cvars -> Extractor: packages/qw-config/scripts/extract-ezquake-cvars-clang.py

command

Console-invoked action. The verb the player types.
What it entails
Named actions the engine executes when typed in the console or bound to a key. Covers connection (connect), gameplay (+attack, impulse), config management (exec, writeconfig), debugging (condump). Schema stores name, description, argument hints, source location, and whether the command is client / server / both.
Why we extract it
Binds target commands. Aliases wrap command sequences. Every consumer that parses or visualizes a config needs to know which tokens are commands vs cvars vs aliases - they're resolved differently. Without this table, a bind chain can't be classified.
Example
bind mouse1 +attack, exec autoexec.cfg, alias wpnext "impulse 10"
Consumers
slipgate bind classifier alias resolver config linters (future)
-> Schema: SCHEMA.md#commands -> Extractor: packages/qw-config/scripts/extract-ezquake-commands-clang.py

keyname

Identifier for a physical key or button in a bind.
What it entails
The string the engine accepts on the left side of a bind command. Includes keyboard (space, mouse1, F1, kp_enter), joystick inputs, and modifier variants. 148 distinct key identifiers in ezQuake. Schema stores canonical name, aliases the engine accepts, and the source enum declaration.
Why we extract it
A config editor or visual bind editor needs to know what's bindable. Rendering a visual keyboard layout, validating user-entered bind targets, and parsing existing bind chains all depend on this list. Keynames are the vocabulary of the input layer - without them, bind mouse4 +attack is indistinguishable from bind asdf +attack.
Example
bind mouse1 +attack, bind F1 "say gl hf", bind kp_end "impulse 2"
Consumers
slipgate BindsView visual keyboard editor (future) bind validator
-> Schema: SCHEMA.md#keynames -> Extractor: packages/qw-config/scripts/extract-ezquake-keynames-clang.py

token primitive

Atomic grammar element the engine tokenizer recognizes.
What it entails
The low-level syntax symbols the engine's config-and-command parser treats as structural: $ for variable expansion, % for teamplay macro, ; for command separator, quote handling rules, whitespace rules, comment markers. 33 primitives in ezQuake. Schema stores the symbol, its role (expansion / separator / quoting / comment / escape), and the parser function that handles it.
Why we extract it
Without knowing the tokenizer's grammar atoms, consumers that walk or lint configs can't safely parse them. Slipgate's alias-chain follower and macro-expansion resolver need to know where $ triggers variable substitution and where ; ends a command. A linter that doesn't respect these primitives will mis-split alias bodies. This table is the config-grammar contract.
Example
In a config line alias check "echo %l; wait; say team ready", the primitives at play are % (macro expansion), ; (command sep), " (quote grouping).
Consumers
slipgate alias-chain resolver slipgate macro / $var display config linter (future)
-> Schema: SCHEMA.md#token_primitives -> Extractor: packages/qw-config/scripts/extract-ezquake-token-primitives-clang.py

macro

Built-in percent-expansion token (%h, %a, %l).
What it entails
Percent-prefixed tokens the engine expands at command-evaluation time, typically inside teamplay binds. %h = current health, %a = armor, %l = current location. 68 macros in ezQuake across combat status, items, map context, and game state. Schema stores name, expansion source (cvar, game state, computed), return type, and description.
Why we extract it
Teamplay configs are dense with macro use. Any pretty-print or what-will-this-say preview needs to expand macros to show the actual message. Consumers that validate teamplay scripts need to know which macros are real and which are typos.
Example
bind t "say_team i have %h/%a at %l"
Consumers
slipgate pretty-view teamsay preview teamplay linter
-> Schema: SCHEMA.md#macros -> Extractor: packages/qw-config/scripts/extract-ezquake-macros-clang.py

cmdline param

Command-line flag passed at engine launch (+set, -game).
What it entails
Flags the engine processes before entering the main loop - different from console cvars or commands. Covers game selection (-game ruleset_smackdown), cvar preseeding (+set fullscreen 1), console dumping, config sourcing, etc. 71 cmdline params in ezQuake. Schema stores flag name, syntax (single flag vs flag+value), description, source location.
Why we extract it
Launcher apps (slipgate) build engine command lines. Knowing which flags are valid, what they accept, and what they do is what lets the launcher offer a sane configuration UI instead of a free-form text box.
Example
ezquake.exe -game ctf +set fullscreen 1 +exec autoexec.cfg
Consumers
slipgate launcher launcher UI (future) cmdline validator
-> Schema: SCHEMA.md#cmdline_params -> Extractor: packages/qw-config/scripts/extract-ezquake-cmdline-clang.py

hud element

Named HUD component the player can show / move / style.
What it entails
Discrete on-screen display components: health bar, armor display, ammo counters, frag tracker, clock, scoreboard panels. Each HUD element has position, visibility, style, and element-specific cvars (hud_health_X, hud_health_place, etc.). 83 HUD elements in ezQuake. Schema stores element name, per-element cvar set, default position, and element category.
Why we extract it
The HUD is one of the most configured parts of a QW client. Any config editor / visualizer needs to know the valid HUD elements to render a preview or to group the hundreds of hud_* cvars by element.
Example
hud_health_place "top", hud_health_show 1
Consumers
slipgate HUD editor (future) HUD preview renderer
-> Schema: SCHEMA.md#hud_elements -> Extractor: packages/qw-config/scripts/extract-ezquake-hud-elements-clang.py

ruleset

Named competition-compatibility preset (smackdown, qcon, default).
What it entails
Canonical rulesets the engine supports - each a bundle of cvar locks and feature restrictions designed for a specific tournament or playstyle. 6 rulesets in ezQuake. Schema stores ruleset name, full locked-cvar list, authoritative source reference, and per-field blame index so historical rule changes are queryable.
Why we extract it
Tournament configs must match ruleset. Slipgate surfaces "you are on ruleset X; these cvars cannot be changed." Historical queries ("when did smackdown lock r_fastsky?") answer from this table + blame index.
Example
ruleset smackdown - locks r_fastsky 1, gl_flashblend 0, etc.
Consumers
slipgate ConfigViewer ruleset diff tool compliance checker
-> Schema: SCHEMA.md#rulesets -> Extractor: packages/qw-config/scripts/extract-ezquake-rulesets-clang.py

flag bit

Individual bit within a cvar/feature flag family (CVAR_ARCHIVE, FPD_NO_FORCE_SKIN).
What it entails
Single bits inside bit-flag families: CVAR_* (cvar metadata: archived, userinfo, server-only), FPD_* (feature disables set by the server), STAT_* (stat IDs transmitted over the wire). 50 flag bits in ezQuake at head. Schema stores family name, bit name, bit value, the family's declaration location, and the bit's purpose.
Why we extract it
A cvar's behaviour depends on its flag bits - CVAR_ARCHIVE means it's saved to config, CVAR_USERINFO means it's broadcast to the server. Knowing individual bits lets consumers explain WHY a cvar behaves as it does, and lets servers / linters reason about FPD restrictions.
Example
cvar_t sensitivity = { "sensitivity", "3", CVAR_ARCHIVE | CVAR_USERINFO }; - the flag bits here define the cvar's lifecycle.
Consumers
slipgate cvar inspector linter explaining cvar scope
-> Schema: SCHEMA.md#flag_bits -> Extractor: packages/qw-config/scripts/extract-ezquake-flag-bits-clang.py

asset category

Classification of engine-loaded files on disk (textures, sounds, models, etc).
What it entails
Top-level categories ezQuake loads: textures (charsets, HUD, map-specific, WAD-bundled), sounds, models (MDL, MD3), configs, maps, demos, screenshots, etc. 17 categories at head. Paired with asset_extensions, asset_path_rules, asset_cvar_bindings, asset_loader_sites relation tables.
Why we extract it
Tools that understand what a user's quake/ directory actually contains need this taxonomy. Slipgate's quake-dir browser uses it to group files sensibly. Future catalog services (assets.quake.world) use it as the axis for search and curation.
Example
File textures/schloss/wall.tga -> category 'map-specific texture'. File qw/ezquake.cfg -> category 'config'.
Consumers
slipgate quake-dir browser assets.quake.world (future) config linter
-> Schema: SCHEMA.md#asset_categories -> Extractor: packages/qw-config/seeds/asset-taxonomy.yaml + AST reconciler
