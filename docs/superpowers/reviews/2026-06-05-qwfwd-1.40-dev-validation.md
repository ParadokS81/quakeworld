### Candidate (a) -- Master-server registration / heartbeat
- **Cross-codebase surface:** QWFWD `masters` + `masters_heartbeat` + `masters_query` + `masters_filter_servers` + `heartbeat` (query.c:697-700 / cmd reg); QTV `masters` (udp.go:67); MVDSV `sv_master*` (sender side); ezQuake (querier side).
- **Phase-3 breadcrumb evidence:** 6 knobs tagged -- the densest of the three candidates. The described knobs reveal a TWO-ROLE concept invisible at the per-cvar level: an announce-self role (`masters_heartbeat`/`heartbeat` -- the proxy sends periodic heartbeats so it stays listed) and a fetch-the-list role (`masters_query` -- the proxy asks the masters for the current server list), with `masters_filter_servers` a blocklist over the fetched list. The same `masters` concept spans qwfwd (registrant + querier), qtv (registrant), mvdsv (sender), and ezquake (querier).
- **Recommendation:** AUTHOR (strong) -- widest cross-codebase span and the clearest "a note ties knobs no single L1 row connects" case. Author it as the FIRST follow-on note.

### Candidate (b) -- MVD streaming + parse_delay ghosting
- **Cross-codebase surface:** QTV `parse_delay` (upstream_storage.go:85, default 7) + `tick_time` (qtv.go:212, default 100) + `address` (the proxy's advertised connect address) + the `qtv` command (opens an upstream MVD connection) <-> MVDSV MVD source (`qtv_*` stream cvars) <-> ezQuake viewer.
- **Phase-3 breadcrumb evidence:** 4 knobs tagged -- a RICH harvest, so the prior's "defer if breadcrumb-thin" condition did NOT trigger. The descriptions make the ghosting mechanism concrete: `parse_delay` holds the stream N seconds behind live so QTV always has data to relay; `tick_time` is the relay cadence; `qtv`/`address` wire the upstream/downstream ends. This is genuine cross-codebase behavior tying qtv timing knobs to the mvdsv source and the viewer.
- **Recommendation:** AUTHOR -- the rich harvest tips the prior from "author-lean" to author. Sequence it after (a).

### Candidate (c) -- qtv_password cross-codebase auth matrix
- **Cross-codebase surface:** QTV `qtv_password` (downstream_storage.go:200, default `""`) <-> MVDSV `qtv_password` (PLAIN/CCITT/MD4/SHA3-512, sv_demo_qtv.c:514/520/529/544, fully documented in the shipped ledger) <-> fteqtv wire protocol (D13: fteqtv is xref-only, never an extraction target).
- **Phase-3 breadcrumb evidence:** 1 knob tagged. The QTV `qtv_password` description already captures the bidirectional nature (as server: a downstream viewer/relay must supply it; as client: this proxy supplies it upstream). The MVDSV ledger already documents the full hashing matrix, and the QTV row is See-also-linkable to it.
- **Recommendation:** DEFER -- single knob, already See-also-wired, and the auth-matrix detail is the protocol's other end, which the MVDSV ledger explicitly judged "not action-changing for the server admin beyond 'set it to require a password'." The earn-the-note bar is not cleared; a full note risks protocol-trivia over actionable guidance. Defer unless the operator wants the negotiation-flow note for its own sake.
