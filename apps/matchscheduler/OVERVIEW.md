# MatchScheduler - Overview

> What this document is: a quick-orientation living map of the scheduler app. For the file-by-file architecture map, read `context/ARCHITECTURE-MAP.md`. For why it exists, read `VISION.md`. For rules, read `CLAUDE.md`.

## Status

Maintenance. Stable and in active use across ~40 teams / ~300 players in the 4on4 scene. No active architectural work. Bug fixes and small tournament-pressure features land; larger improvements get deferred to the slipgate web rebuild.

## What's here

### Frontend (`src/`, `public/`)

- **Vanilla JS + Alpine.js + Tailwind**. The 3x3 grid is a fixed layout; changing it is explicitly out of scope.
- **CSS pipeline** - edit `src/css/input.css` only; `public/css/main.css` is generated by the build.
- **Component pattern** - Revealing Module (simple widgets) or Alpine.js (reactive components). No React / Vue / Svelte. Ever.
- **Firebase listeners** - components own their own Firestore listeners. Services manage cache only. The pattern is "Firebase -> Component -> UI + Cache." Never middleware/subscription services.

### Backend (`functions/`, `firestore.rules`, `firestore.indexes.json`)

- **Cloud Functions** for Discord OAuth exchange (`discordOAuthExchange`) and select writes.
- **Firestore rules** enforce team membership, captain-only writes, and cross-team read permissions.
- **Firestore indexes** live under version control and ship with every deploy.

### Data contracts

- Firestore schema lives in `context/SCHEMA.md`. Authoritative document.
- Cross-project contracts (shapes Quad and qw-stats depend on) live in `/contracts/CROSS-PROJECT-SCHEMA.md` at monorepo root. Any change to those shapes touches this file AND the writer/reader in the same commit.

## Integration points

### qw-stats (HTTP API, read-only)

The scheduler fetches head-to-head and form data from the qw-stats Express API (`/api/h2h`, `/api/form`, `/api/maps`, `/api/roster`). Deployed on ParadokS's Unraid server, reached via Tailscale. Match pages render these inline.

### Quad (Firestore, cross-collection)

- **`voiceRecordings/{demoSha256}`** - written by Quad after voice-to-demo pairing. Read by the scheduler's match page to hydrate the voice-replay player. The SHA256 is the join key; the scheduler does not own this collection.
- **`standin_requests/{requestId}`** - written by the scheduler when a team needs a substitute. Read by Quad to post DM polls to candidate players.
- **`standin_preferences/{discordUserId}`** - written and read by both sides; opt-out and block settings for the DM flow.

### QW Hub (external)

- **Supabase REST** (`ncsphkjfominimxztjip.supabase.co/rest/v1/v1_games`) - match history polling.
- **ktxstats CDN** (`d.quake.world/{sha[0:3]}/{sha}.mvd.ktxstats.json`) - per-match ktxstats used to enrich match pages.

### Discord (social layer)

Discord OAuth is the primary login. Sealed-match embeds, challenge posts, and confirmation embeds get POSTed to team-configured channels via webhook.

## Firebase emulator

**Always running during dev. Do not restart it.**

- Firestore UI: `http://localhost:8080`
- Functions logs: `http://localhost:5001`
- Seed with `npm run seed:quick` (or `npm run seed` for the full seed including team logos)
- Dev dataset uses fixed UIDs - see `docs/DEV-SETUP.md`

## Shared Firebase project

The dev emulator and production both run under the `matchscheduler-dev` Firebase project. slipgate-app uses the same project for Discord OAuth (via the shared `discordOAuthExchange` Cloud Function). That coupling is real: breaking OAuth here breaks login in slipgate-app.

## Scale

- ~300 active players
- ~40 teams
- 4 weeks of availability visible at a time
- Players can be on max 2 teams
