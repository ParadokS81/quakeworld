# MatchScheduler - Overview

> What this document is: a quick-orientation living map of the scheduler app. For the file-by-file architecture map, read `context/ARCHITECTURE-MAP.md`. For why it exists, read `VISION.md`. For rules, read `CLAUDE.md`. Open work is in the monorepo's root `HANDOVER.md`.

## Status

Maintenance. Stable and in active use across ~40 teams / ~300 players in the 4on4 scene. No active architectural work. Bug fixes and small tournament-pressure features land; larger improvements get deferred to the slipgate web rebuild.

## What's here

### Frontend (`public/`, CSS source in `src/css/`)

- **Vanilla JS + Alpine.js + Tailwind**, shipped as plain files from `public/` (no bundler). The 3x3 grid is a fixed layout; changing it is explicitly out of scope.
- **Two mobile tiers.** Landscape tablets (`max-width: 1024px` and landscape) keep the desktop grid and move the side panels into drawers (`MobileLayout.js`, `MobileBottomBar.js`; rules in `public/CLAUDE.md`). Phones (`max-width: 768px`) get a separate portrait-first app under `public/js/mobile/` that shares the desktop services and edits availability, proposals and team settings (`public/js/mobile/CLAUDE.md`).
- **Hash router** (`public/js/Router.js`) - deep links to a team's history or head-to-head view, a proposal, team settings, the players tab.
- **Installable** as a PWA (`manifest.json`, `sw.js`).
- **Extra pages** - `replay.html` (voice replay: the Hub demo player in an iframe with per-player audio tracks from Firebase Storage), `ktx-documentation.html` (a static KTX Layer 1 audit catalog, published 2026-05), `auth/discord/` (the OAuth callback).
- **CSS pipeline** - edit `src/css/input.css` only; `public/css/main.css` is generated by `npm run css:build`.
- **Component pattern** - Revealing Module (simple widgets) or Alpine.js (reactive components). No React / Vue / Svelte. Ever.
- **Firebase listeners** - components own their own Firestore listeners. Services manage cache only. The pattern is "Firebase -> Component -> UI + Cache." Never middleware/subscription services.

### Backend (`functions/`, `firestore.rules`, `storage.rules`, `firestore.indexes.json`)

- **46 v1 Cloud Functions** in `europe-west3`, one container (`functions/index.js` is the export list): sign-in and profiles (`googleSignIn`, `discordOAuthExchange`, profile CRUD, `deleteAccount`); team operations (create / join / leave, join codes, tags, phantom members, recording visibility and deletion); availability and templates, including recurring auto-apply; favorites; the proposal lifecycle (`createProposal`, `confirmSlot`, `withdrawConfirmation`, cancel, `quickAddMatch`, `rescheduleMatch`, scheduler toggle); feedback; Discord bot registration; Mumble enable / disable / settings; the Big4 manual sync; admin weekly stats; and two plain HTTPS endpoints, `getScheduledGames` (unauthenticated, CORS-open, 60 s cache, built for QWHub) and `helloWorld`.
- **2 v2 storage triggers** in `europe-west10`: `processLogoUpload`, `processAvatarUpload`.
- **Scheduled jobs** (Pub/Sub cron): proposal expiry and recurring-template apply on Mondays, weekly stats on Mondays, scheduled-match expiry every 30 minutes. The 15-minute Big4 poll was retired 2026-09-11 (`DEPLOYMENT.md`, "Retired scheduled functions").
- **Firestore rules** - reads are open to authenticated users (teams and user profiles even to guests, for browsing); writes go through Cloud Functions (`allow write: if false` on most collections), with `availability`, a user's own profile and team create / update left open to authenticated clients for the dev-mode direct-write path and validated in the functions in production. Summary table in `context/SCHEMA.md`.
- **Firestore indexes** live under version control and ship with every deploy.

### Data contracts

- Firestore schema lives in `context/SCHEMA.md`. Authoritative document.
- Cross-project contracts (shapes Quad and qw-stats depend on) live in `/contracts/CROSS-PROJECT-SCHEMA.md` at monorepo root. Any change to those shapes touches this file AND the writer/reader in the same commit.

## Integration points

### qw-stats (HTTP API, read-only)

`QWStatsService.js` calls the qw-stats Express API at `https://qw-api.poker-affiliate.org` (`/api/h2h`, `/api/form`, `/api/maps`, `/api/roster`, `/api/opponents`): a public Cloudflare tunnel in front of the `qw-stats-api` container on the Unraid box, called from the browser. The team browser's history and head-to-head tabs render the results inline.

### Quad (Firestore, shared collections)

Quad is the Discord bot and voice recorder; the two apps meet in Firestore, never directly:

- **`botRegistrations/{teamId}`** - the Discord bridge: this app creates and disconnects (`manageBotRegistration`), Quad activates and syncs; holds channel config, guild members and the unified auto-record settings (enabled, min players, platform).
- **`mumbleConfig/{teamId}`** - the same pattern for Mumble: `enableMumble` writes a pending config, Quad creates the channel on `mumble.slipgate.me`; the Mumble tab in team settings shows join links (`join.slipgate.me/<channel>`, shareable in Discord).
- **`notifications/{id}`** - challenge, confirmation and sealed-match embeds: written by the proposal functions, delivered to the team's Discord channel by Quad.
- **`voiceRecordings/{demoSha256}`** - written by Quad after a recording is paired with a demo; read by this app's recordings UI and replay page; `updateRecordingVisibility` / `deleteRecording` write back, and **`deletionRequests/`** carries the cross-system delete.
- **`recordingSessions/`**, **`weeklyStats/`** - admin-only views (`AdminPanel.js`, `AdminStatsDisplay.js`).
- **Not built here** - `standin_requests` / `standin_preferences`. The contract lists this app as the writer and Quad has the listener, but nothing in this codebase writes them; the in-app "Find standin" is a local availability filter (`StandinFinderService.js`). Tracked in the root `HANDOVER.md`.

### QW Hub (external)

- **Supabase REST** (`ncsphkjfominimxztjip.supabase.co/rest/v1/v1_games`) - match history (`QWHubService.js`; endpoint reference in `context/QWHUB-API-REFERENCE.md`).
- **ktxstats CDN** (`d.quake.world/{sha[0:3]}/{sha}.mvd.ktxstats.json`) - per-match stats; **mapshots** from `a.quake.world`; match and demo-player links into `hub.quakeworld.nu`.

### The Big 4 (external, dormant)

`big4-sync.js` imports fixtures from `thebig4.se` into `scheduledMatches` (origin `big4_import`). The league closed after Season 2 and its API 404s; the scheduled poll is retired and only the manual callable `syncBig4Matches` remains (no UI; `scripts/test-big4-sync.js`). Revival terms are in the root `HANDOVER.md`.

### Discord (social layer)

Discord OAuth and Google are the two sign-ins (`UserProfile.js`); the OAuth exchange is the Cloud Function `discordOAuthExchange`, which slipgate-app also calls. Match embeds go out through Quad (above). A popup guard in `AuthService.js` keeps a sign-in alive when a tiling window manager resizes the browser across the mobile breakpoint mid-flow.

## Shared Firebase project

One Firebase project, `matchscheduler-dev`, serves production (the name is historical; `.firebaserc` has no other project). slipgate-app uses the same project for Discord OAuth (via the shared `discordOAuthExchange` Cloud Function). That coupling is real: breaking OAuth here breaks login in slipgate-app.
