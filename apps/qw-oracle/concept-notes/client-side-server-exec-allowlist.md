# Client-side server-exec allowlist: guarding the client against hostile servers

## Summary

ezQuake 3.6.6 introduced a coordinated client-side defense against hostile or compromised servers abusing the QuakeWorld protocol's ability to push command-buffer text to connected clients. Three new cvars (`cl_allow_downloads`, `cl_allow_uploads`, `cl_remote_capabilities`) define a policy layer: which files may be received, whether the client will serve files back, and which client-side commands and cvars a server is allowed to invoke. Four additional fixes close adjacent surfaces the same policy was meant to cover: the `qw://` URL parser now rejects command-concatenation characters, `exec` refuses to run files with downloadable-file extensions, and client-authored aliases no longer pass through the server-facing command buffer. All of this landed across PRs #976, #979, #981, #984, #992, and #994 in a concentrated burst between 2024-12-14 and 2025-01-12 with Oscar Linderholm (`@osm`) as primary author.

## The threat model

QuakeWorld's wire protocol has always included server-to-client command transport. Servers use it for legitimate things: kicking a client into a spectator slot, forcing a reconnect, invoking KTX match hooks like `on_matchstart`, setting display strings. The mechanism is `stufftext` on the wire, which the client reads into a dedicated command buffer called `cbuf_svc` and executes through the same command dispatch used for user input. Historically, `cbuf_svc` accepted essentially any command the server chose to send. Combined with two other protocol capabilities - the server can request the client download or upload files, and the client has a URL-scheme handler (`qw://`) that can be triggered from browsers or shell integrations - this created a broad attack surface where a hostile server could:

- Stuff arbitrary commands into the client's command buffer (`stufftext` into `cbuf_svc`).
- Ride client-defined aliases whose expansions re-entered `cbuf_svc` unfiltered.
- Force downloads of file types the client was not prepared to receive, then trick the user (or the engine) into `exec`-ing the result.
- Inject a second command through the `qw://` URL handler by concatenating with `;` in the URL.

No single new exploit triggered this cluster; the commits treat the whole surface as a policy gap rather than a specific CVE. The fixes are authored-by and credited to `@osm` (Oscar Linderholm) in every case and every commit message frames the change as "prevent," "restrict," or "validate" rather than citing a public disclosure.

## The three-cvar policy

All three cvars were added together in PR #979 (`osm/add-remote-capabilities-validation`, merged as `1678bb1c` on 2025-01-02). The branch name frames the whole set as "validation" - a layer of client-side permission checks over server-initiated operations.

- **`cl_allow_downloads`** (commit `41852d49`, default `"bsp,lmp,loc,mdl,mvd,pcx,spr,wad,wav"`) is a comma-separated allowlist of file extensions the client will accept from the server. Replaced the older single-purpose `cl_allow_download_file_extensions` cvar. The default is the canonical safe set: map files, demos, point files, sprites, sounds, and model/texture assets - nothing that maps onto a config file, script, or native binary. Enforcement at `src/cl_cmd.c:632-635` inside `CL_Download_Accept`, which rejects any incoming file whose extension is not in the list.
- **`cl_allow_uploads`** (commit `c04f608d`, default `"0"`) is a boolean toggle for whether the server may upload files from the client's quake directory to itself. Default off. A server that wants a client's config or demo for troubleshooting has to ask the user to enable the cvar first. The help entry in `help_variables.json` for this cvar has no `desc` field - the extractor emits only default, group-id, and type. That gap is inherited by ezquake.com's autogenerated reference page and is flagged as an upstream help-text gap.
- **`cl_remote_capabilities`** (commit `b276b1d0`, default `REMOTE_CAPABILITIES` macro at `src/cmd.c:61-66`) is a comma-separated allowlist of commands and cvars the server may invoke on the client via `cbuf_svc`. The default list contains 44 entries: attack-binding toggles (`+attack`, `-attack`), KTX match-state hooks (seventeen `on_*` aliases including `on_connect`, `on_matchstart`, `on_observe_ctf`), infoset family (`infoset`, `sinfoset`, `ktx_infoset`, `ktx_sinfoset`, `tempalias`), and core engine controls the protocol has always relied on (`changing`, `track`, `reconnect`, `say`, `team`, `color`, `skin`, `rate`, `exec`, `download`, `cmd`, `alias`, `bf`, `fullserverinfo`, `impulse`, `nextul`, `packet`, `play`, `wait`). Enforcement at `src/cmd.c:1890-1892` (commands) and `src/cmd.c:1909-1911` (cvars): when `cbuf_current == &cbuf_svc` and the token is not in the `rc_hash` populated from this cvar, the dispatch prints `"Blocked <name>: not in cl_remote_capabilities"` and returns.

The cvar has one more piece of validation worth naming: the `OnChange_remote_capabilities` handler at `src/cmd.c:84-92` refuses any edit unless `cls.state == ca_disconnected`. That closes the obvious self-referential bypass - a server cannot stuff `set cl_remote_capabilities +attack,-attack,...,set` to widen its own permission set at runtime, because the cvar refuses to mutate while connected. Operator tuning happens in `config.cfg`, not mid-game.

## Other attack surfaces closed

The cvar policy alone does not cover every path a hostile server has to client-side execution. Three adjacent commits close the rest:

**URL parser (`qw://` scheme, commit `6788b031`, PR #976, 2024-12-14).** `CL_QWURL_f` at `src/cl_main.c:734-740` now calls `strchr(Cmd_Argv(1), ';') != NULL` on the URL argument and rejects the whole string with `"The QW-URL \"%s\" contains illegal characters"` if a semicolon is present. The console uses `;` as a command separator, so a URL like `qw://server.example.com:27500;say pwned` would previously parse as a connect followed by a second command; the check blocks that class of injection at the URL entry point. The PR branch name (`upstream-qw-url-parser-fix`) suggests the fix was ported from an upstream QW engine rather than authored from scratch for ezQuake.

**`exec` of downloaded files (commit `57416b00`, PR #981, 2025-01-02).** Commit message: "Prevent downloadable files from being executed. This ensures that no file a server uploads to your client can be executed." The implementation pulls the download-allowlist check out of `CL_Download_Accept` into a reusable predicate `CL_IsDownloadableFileExtension` (`src/cmd.c:140-159`) and calls it from `Cmd_Exec_f` (`src/cmd.c:566-569`). If the file being `exec`-ed has an extension in `cl_allow_downloads`, `exec` refuses with `"\"%s\" is not allowed to be executed. Remove \"%s\" from cl_allow_downloads to allow execution"`. The logic is deliberately inverted: the set of extensions safe to *receive* is exactly the set that must *not* be `exec`-ed, because any file in that set could have been server-planted. A user who wants to `exec` one of their own `.mvd` demo overlays or `.loc` commentary files has to shrink `cl_allow_downloads` first.

**`cbuf_svc` alias routing (commit `37922152`, PR #992, 2025-01-11).** In the old code at `src/cmd.c:1973-1975`, any alias expanded while running in `cbuf_svc` re-inserted its expansion back into `cbuf_svc`. After the fix: `inserttarget = is_server_alias ? &cbuf_svc : &cbuf_main;`. Server-defined aliases (marked `ALIAS_SERVER`, created via `tempalias` or server-stuffed `alias` commands) continue to flow through `cbuf_svc` where the remote-capabilities check gates their contents. Client-authored aliases whose names happen to be in the allowlist now have their expansions routed to `cbuf_main` instead, so a server that stufftexts a client alias name only triggers the alias invocation, not a re-entry of the expanded contents through the server command buffer. This narrows what a server-triggered alias expansion can reach without widening what a server-stuffed command can do.

## Iteration story: the Jan 2025 KTX tuning

The default `REMOTE_CAPABILITIES` list shipped in the 2024-12-30 commit was immediately tested against real KTX server behavior and adjusted over the next two weeks. Three follow-up commits show the feedback loop:

- **Commit `5a124533` (PR #984, 2025-01-03) "Allow server to stufftext `{+,-}attack`."** The commit message documents the exact use case: "When using wreg and spectating on a KTX server, {+,-}attack commands are issued when firing." Weapon-register (`wreg`) scripts on KTX are server-generated and rely on being able to stufftext `+attack`/`-attack` into the client command buffer for correct firing behavior in spectator mode. These two commands had been left out of the initial allowlist; adding them unblocked standard KTX match spectating.
- **Commit `989ec708` (PR #994, 2025-01-03) "Add rate to cl_remote_capabilities."** Servers set `rate` on connecting clients for fairness and anti-cheat reasons; the initial list was too strict.
- **Commit `94080d53` (PR #994, 2025-01-11) "Update defaults for cl_remote_capabilities."** Adds twelve additional `on_*` aliases: `on_admin`, `on_connect`, `on_connect_ctf`, `on_connect_ffa`, `on_matchend`, `on_matchstart`, `on_observe`, `on_observe_ctf`, `on_observe_ffa`, `on_spec_matchend`, `on_spec_matchstart`, `on_unadmin`. These are KTX event hooks - client-side alias names KTX invokes at specific match transitions. An operator whose server called any of them against a 3.6.6 client running the original default would have seen the block message and would have lost their HUD/overlay updates at match start. The iteration converged by about 2025-01-12 with the final 44-entry list.

The shape of this iteration is instructive: an initial allowlist landed, real server behavior exercised it, each gap surfaced as a "Blocked X: not in cl_remote_capabilities" line in the client console, and operators fed the list back to the engine maintainers. The default is what shipped in 3.6.6; individual operators can tighten or loosen it per their own policy.

## Consumer implications

- **Oracle MCP "what does cl_remote_capabilities do" queries** - the Layer 1 entry carries the default string and a one-line `desc`, which is enough to know there is an allowlist but not enough to know what the policy protects against. The three-layer answer shape is: Layer 1 supplies the cvar row, this note supplies the threat model and the pattern. Without the note, an operator reading the cvar reference sees 44 comma-separated names with no framing for why they are there.
- **Oracle MCP "why does my server see 'Blocked X: not in cl_remote_capabilities'" queries** - the answer is operational (the server is trying to issue a command the client has allowlisted out) not diagnostic (nothing is broken). The appropriate next step depends on who the client trusts: add the command to the client's cvar if the server is trusted, or lean on the block if it is not. The cvar requires disconnect to edit, so operators cannot silently widen their own permissions.
- **Oracle MCP "is this file safe to exec" queries** - `exec` now refuses any file whose extension is in `cl_allow_downloads`. A user asking whether their `.loc` overlay file is safe to execute is asking a question that now has a direct engine-level answer: no, and the engine will reject the `exec` itself.
- **Server operators distributing scripts** - a server that wants its clients to run a custom alias at match start needs the alias name to appear in the client's `cl_remote_capabilities`. Deploying the alias via `tempalias` works by default (the command itself is allowlisted and creates an `ALIAS_SERVER` alias that flows through `cbuf_svc`); deploying it by name expects the name to already be allowlisted. Operators shipping new `on_*` hook names should coordinate with engine maintainers to get them into the default list rather than asking each client to widen their cvar.
- **Tooling consumers (slipgate, config-viewer)** - `cl_allow_downloads` and `cl_remote_capabilities` are both user-tunable string cvars with security semantics. A config-viewer should surface them alongside other security-policy cvars and render the comma-separated value as a readable list, not as a raw string. `cl_allow_uploads` is a simple toggle but has security weight; it should be in the same group.
- **Documentation (upstream)** - ezquake.com currently has no page covering the threat model or the pattern. The three cvars appear in the autogenerated settings reference; the URL-parser, exec, and `cbuf_svc` fixes have no reference home at all. The proposed upstream home is a new page under Features (or a new top-level "Security" sidebar section) on ezquake.com - a new-page PR that also touches the vitepress sidebar config.
